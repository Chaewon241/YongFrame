# 게임 워크로드 부하 재측정 (충돌, 구역, 재생, 이동 속도 360 이후)

- **질문:** 이동 충돌, 건설 구역, 노드 재생 위치 변경, 이동 속도 360 cm/s가 들어간 서버가 같은 합격 기준으로 방을 몇 개까지 처리하는가. 특히 이전에 합격했던 방 500개가 여전히 합격하는가.
- **계획과 합격 기준:** [docs/stage4.md](../../docs/stage4.md)의 "부하 재측정 계획"(측정 전에 작성)과 그 위 "부하 측정 계획"의 합격 기준. 합격 기준은 바꾸지 않았다. 이전 측정: [game-load.md](game-load.md).
- **한 번에 한 변수가 아니다.** 충돌, 속도 360, 재생/구역 로직이 함께 바뀐 서버 전체를 이전 서버와 비교했다. **어느 변경이 비용을 얼마나 늘렸는지는 가르지 못했다.**
- **바꾼 변수:** 방 수(100, 300, 400, 450, 500, 600). 조건 (가)는 방마다 구조물 0개, 조건 (나)는 방마다 완공된 집 20개(`--bench-prebuilt-structures 20`)로 방 500개만 쟀다. **고정한 것:** Release 빌드(MSVC 14.44), 서버 `--log-level info --stats-interval 1`, `io_context` 스레드 1개, `TCP_NODELAY` 켬, 생성기 `--threads 4`, 방당 4명, 플레이어당 `MoveInput` 초당 10번, 워밍업 5초, 측정 30초, 반영 대기 최대 3초, 조건당 3회, 매 실행 새 서버 프로세스.
- **추가 조건에 대한 기록:** 계획대로 (가) 100, 400, 500, 600개와 (나) 500개를 쟀다. (가) 500개가 3회 모두 합격하지 못해, **미리 정한 규칙**에 따라 (가) 300개와 450개를 더했다(결과를 보기 전에 정한 규칙이고 합격 기준은 그대로다). (가) 600개는 합격하지 못해 700개는 더하지 않았다.
- **환경:** `raw/game-load-recheck-environment-main.txt`(본 측정)와 `raw/game-load-recheck-environment.txt`(300/450개 추가 측정 시작 때). Ryzen 5 5600(6코어 12스레드), RAM 16 GB, Windows 11, **같은 PC 루프백**, 측정 시작 때 배경 프로그램은 chrome, EpicGamesLauncher, Discord 등이었고 그 외 부하는 없었다(전체 CPU 약 6%). 서버 코드는 커밋 `03722ec`에 **부하 측정 전용 옵션(`--bench-prebuilt-structures`, 기본 0)을 더한 것**이다(이 옵션이 0이면 동작이 같다). 환경 파일의 "커밋되지 않은 변경 84개"는 측정 결과 파일과 이 옵션 등을 센 것이다.
- **원본:** `raw/game-load-recheck.csv`((가) 18회), `raw/game-load-recheck-structures.csv`((나) 3회), 실행별 화면 출력 `raw/game-recheck-<조건>-r<방>-rep<회차>.txt`(한글이 깨져 보이는 것은 생성기가 콘솔 코드 페이지로 쓴 출력이라서이며 숫자는 읽힌다), 서버 로그 `raw/game-server-recheck-*.log.gz`. 집계는 `aggregate.py`(통계 줄 형식이 길어져서 정규식 끝을 고쳤다), 실행 도구는 `run-load-recheck.ps1`이다.

## 정정: 이 결과를 어떻게 읽어야 하는가 (이후 실험으로 알게 된 것)

**이 문서의 "최대 안정 방 수 450개", "방당 CPU 15~27% 증가"는 확정된 결론이 아니다.** 이 재측정 뒤에 한 두 실험이 그 해석을 약하게 만들었다.

1. **원인 분해 실험**(방 400개, 같은 세션에서 속도 360/300, 충돌 켬/끔을 번갈아): 서버 CPU가 모두 61~64%로 같았다(차이 3%포인트 미만). **이동 속도와 이동 충돌은 비용의 원인이 아니었다.** 그런데 이 세션에서 방 400개 새 서버의 CPU가 60.7%로, 위 재측정(84.3%)과 이전 측정(70.7%)보다 낮았다. 같은 코드가 세션마다 20% 넘게 다르게 나온 것이다.
2. **이전 서버(측정 당시 커밋 `cb9d3c8`)와 새 서버를 같은 세션에서 번갈아 재려던 비교는 무효가 되었다.** 그 세션에서 PC의 다른 프로그램(게임과 안티치트 서비스)이 CPU를 크게 써서, 이전에 방 500개와 400개를 합격했던 이전 서버마저 3회 모두(400개는 1회) 불합격했고(서버 CPU 93~96%), 새 서버의 400개 실행은 생성기 포화로 판정 불가(종료 코드 3)였다. 그 실행들은 `raw/game-load-ab.csv`에 남아 있으나 **결론에 쓰지 않는다.** 이전 서버가 이전 측정 때와 다르게 불합격했다는 것이 "측정한 날의 PC 상태가 결과를 바꾼다"는 증거다.
3. 따라서 이 재측정의 "450개 합격, 500개 불합격"은 **그 세션에서 그랬다**는 기록으로만 남긴다. 이전 서버와의 차이(코드 때문인지, 그날의 PC 상태 때문인지)는 **아직 모른다.** 이 재측정이 이루어진 시간대에 다른 프로그램이 CPU를 얼마나 썼는지는 기록하지 못했다(시작 때 전체 CPU 약 6%만 확인).

**측정이 믿을 만하려면:** PC에서 게임, 브라우저의 영상, 런처 같은 배경 프로그램을 끄고, 이전/새 서버를 같은 세션에서 번갈아 재야 한다. 서버 CPU를 측정 중에도 같이 샘플링한 전체 CPU와 함께 기록하면 오염된 실행을 걸러낼 수 있다(아직 생성기에 없다).

## 해석

1. **이 구성에서 합격 기준을 3회 모두 통과한 최대 방 수는 450개(플레이어 1,800명)다.** 이전에 합격했던 500개는 이제 3회 모두 불합격이다. **이전 구성 대비 약 10% 줄었다.**
2. **500개가 불합격한 직접 이유는 누락 스냅샷 비율(1% 이하 기준)이다.** 도착 간격과 입력 반영 p99는 100 ms 안에 있었다(58 ms, 96 ms). 누락 수가 모두 2,000의 배수이고(클라이언트 2,000명이 동시에 하나씩 놓침) 서버의 최대 틱 처리 시간이 54~61 ms로 틱 간격 50 ms를 넘는 때가 있었으며 서버 CPU가 약 99%였다. 즉 서버가 한 틱을 가끔 밀리는 한계 근처다.
3. **방당 서버 CPU가 약 15~27% 늘었다**(100개 0.21에서 0.25%, 300개 0.17에서 0.22%, 400개 0.18에서 0.21%). 선형성은 그대로다. 이것이 한계 방 수가 500에서 450 근처로 내려온 원인이다. **원인은 가르지 못했다:** 이동 속도 360(같은 시간에 더 많이 움직임), 이동마다 근처 장애물(노드 50개와 구조물)을 훑는 충돌 계산, 재생 로직이 함께 바뀌었다. 이 측정만으로는 어느 것이 큰지 모른다.
4. **방당 구조물 20개(조건 나)가 조건 (가)와 눈에 띄게 다르지 않았다.** 다만 두 조건 모두 500개에서 서버 CPU가 99%로 포화라서 CPU 차이를 볼 수 없고, 누락 수는 실행마다 편차가 컸다(12,000~42,000). **구조물의 비용이 작다고 결론 내리지는 않는다.** 포화하지 않은 방 수(예: 400개)에서 구조물 조건을 재야 비교할 수 있다. 재지 않았다.
5. 600개는 이전처럼 시뮬레이션 시간은 지키면서(서버가 처리한 틱 595~601개) 스냅샷이 줄어드는 모양으로 불합격했다.

## 알려진 문제와 한계

- 원인 분해를 하지 않았다(위 3). 어느 변경이 방당 CPU를 올렸는지는 모른다.
- 이 워크로드는 이동만 보낸다. 노드는 건설 구역 밖에 있고 플레이어는 중앙 주변만 돌아다녀서 **노드와의 충돌은 거의 일어나지 않았고**, 측정된 비용은 "근처 장애물 추리기"가 대부분이다. 실제 게임에서 사람이 노드와 집 사이를 비비며 움직이는 비용은 재지 않았다. 채집과 건설 요청이 섞인 워크로드도 재지 않았다.
- 조건 (나)의 집은 시작 위치와 중앙 줄을 비운 격자라 접촉은 일부만 일어난다.
- 방 450개와 500개 사이는 재지 않았다(최대 안정 방 수는 450 이상 500 미만이다). 450개는 서버 CPU 90%에서 3회 모두 합격했다.
- **중간 실행 실수:** 추가 조건을 처음 시작할 때 방 수 목록(`300,450`)을 명령줄에서 쉼표 때문에 하나의 숫자(300450개)로 읽어, 잘못된 값으로 한 번 돌았다. 곧바로 중단하고(생성한 프로세스 3개만 번호로 종료) 그 실행의 파일과 기록을 지운 뒤 300개와 450개를 따로 다시 돌렸다. 위 결과에는 그 실행이 들어 있지 않다. 이 실수는 서버 측정값에 영향을 주지 않는다.
- 같은 PC의 루프백, Windows, Release, 이 PC 한 대의 결과이며 Linux 결과는 없다. 조건당 3회다.

## 결정

- **최대 안정 방 수를 방 450개(플레이어 1,800명)로 갱신해 기록한다.** 이전 500개는 충돌 이전(속도 300) 구성의 결과다.
- 방당 CPU가 늘어난 원인을 가르려면 한 번에 하나씩 되돌려 재는 비교(속도만 300으로, 충돌 훑기만 끄기 등)가 필요하다. 지금은 하지 않았다. 최적화는 병목 증거가 있을 때만 하는 원칙에 따라, 먼저 원인 분해를 한 뒤 필요하면 근처 장애물 검색(예: 격자 분할)을 고려한다.
- 이 결과로 방 한 개의 상한이나 게임 규칙을 바꾸지 않는다. 게임 기획의 동시 접속 목표(방당 최대 4명)가 이보다 낮다면 450개로도 충분하다.
