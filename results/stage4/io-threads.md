# 소켓 입출력 스레드 분리 (개선 후보 A) 부하 측정

- **질문:** 게임 로직은 스레드 하나로 두고 소켓 읽기/쓰기를 입출력 스레드 N개로 나누면, 같은 합격 기준으로 방을 몇 개까지 처리하는가. 틱 스레드의 전송(Deliver) 시간은 얼마나 줄어드는가.
- **계획과 합격 기준:** [docs/stage4.md](../../docs/stage4.md)의 "송신 스레드 분리 (개선 후보 A) 구현과 측정 계획"(측정 전에 작성). 합격 기준은 부하 측정 계획의 표 그대로이며 바꾸지 않았다.
- **바꾼 변수:** 입출력 구조 하나. `PRE`(분리 이전 서버: `session.*`/`server.*`만 커밋 `03722ec` 버전, 게임 코드와 측정 옵션은 같음), `IO0`(새 코드, `--io-threads 0`), `IO1`, `IO2`, `IO4`(`--io-threads 1/2/4`). 방 수는 500, 600, 400개(이 순서)이고, 규칙에 따라 600개를 3회 모두 통과한 `IO2`, `IO4`만 700개를 더 쟀다.
- **고정:** Release(MSVC 14.44), `--log-level info --stats-interval 1`, 생성기 `--threads 4`, 방당 4명, 입력 초당 10번, 워밍업 5초, 측정 30초, 조건당 3회, 매 실행 새 서버. 방 수마다 `PRE, IO0, IO1, IO2, IO4`를 한 바퀴로 3바퀴 번갈아 실행. 실행 도구 `run-load-io.ps1`, 집계 `analyze_io.py`.
- **환경:** `raw/game-load-io-environment.txt`. Ryzen 5 5600(논리 프로세서 12개), Windows 11, 같은 PC 루프백, **부하 생성기와 서버가 코어를 나눠 쓴다.**
- **원본:** `raw/game-load-io.csv`(45회), `raw/game-load-io-r700.csv`(6회), 진행 기록 `raw/game-load-io*-progress.txt`(매 실행 직전 PC 전체 CPU와 실행 중 평균/최대), 서버 로그 `raw/game-server-io*-*.log.gz`, 화면 출력 `raw/game-io*-*.txt`.

## 사전 판정 규칙 대조

1. **방 수가 늘었는가:** 예. `PRE`는 500개에서 3회 모두 불합격(누락 4.8~7.8%)인데 `IO2`는 600개, `IO4`는 700개까지 3회 모두 합격했다.
2. **틱 스레드의 전송 부담:** 방 400개에서 전송 시간이 `PRE` 759 ms/s에서 `IO2` 57, `IO4` 58 ms/s로 **92% 줄었다**(기준 30% 이상). 틱 스레드는 메시지를 한 번 만들어 연결로 넘기기만 한다.
3. **분리 구조 자체의 비용(`IO0` 대 `PRE`):** **있다.** 방 400개에서 `IO0`의 서버 CPU 중앙값이 `PRE`보다 8.1%포인트 높고 합격이 2/3이며, 방 500개와 600개에서는 3회 모두 `PRE`보다 누락이 많았다(14.7% 대 6.7%, 30.8% 대 20.5%). 입출력 스레드를 따로 두지 않아도 strand와 원자 변수, 읽기 완료를 한 번 더 넘기는 비용이 든다. 단 방 400개의 `IO0` 편차가 크다(67~95%).
4. **개선이 없는 경우:** `IO1`(입출력 스레드 1개)은 **개선이 아니라 악화**다(아래).

## 해석

1. **입출력 스레드 2개 이상이면 틱 스레드가 병목에서 벗어난다.** 틱 스레드의 단계별 시간 합이 방 600개에서 약 110 ms/s(코어의 11%)로 내려갔다. `PRE`는 같은 일에 약 880 ms/s였다. 방 수를 늘리는 한계가 틱 스레드에서 소켓 송신 시스템 호출을 하는 입출력 스레드로 옮겨 갔다.
2. **스레드 수에 따라 한계가 다르다:** `IO2`는 700개에서 입력 반영 지연이 튀었고(3회 중 2회 불합격), `IO4`는 700개에서도 3회 합격했다. `IO4`의 입력 반영 p99가 `IO2`보다 낮다(60 대 70 ms 안팎).
3. **대가:** 같은 부하를 처리하는 데 서버 프로세스 전체 CPU가 늘었다(방 400개: `PRE` 85%, `IO2`/`IO4` 105%, 약 25% 증가). 비동기 쓰기를 strand로 넘기고 완료를 처리하는 비용이다. 방 500개 이상에서는 `PRE`가 코어 하나에 붙어(99%) 더 못 처리하는 반면 `IO`들은 여러 코어를 쓴다.
4. **`IO1`은 쓰면 안 되는 설정이다.** 입출력 스레드 하나가 송신 완료 처리와 읽기를 모두 맡다 포화되어, **누락 스냅샷은 0인데 입력 반영 지연이 6~11초로 늘었다**(방 500개 6.3초, 600개 11.1초). 읽기 완료가 송신 작업 뒤에 밀려 입력이 늦게 논리 스레드에 도착하고, 논리 스레드는 계속 스냅샷을 연결 큐에 쌓는다. 도착 간격 p99는 기준 안이라서 **간격만 보면 놓친다.** 합격 기준에 입력 반영 지연이 있어서 잡혔다. 이 상태가 계속되면 연결당 송신 큐 한도(4 MiB)까지 쌓이다 끊긴다. 아래 "알려진 한계" 참고.

## 알려진 한계

- **PC가 완전히 조용하지는 않았다.** 사용자가 정한 대로 매 실행 직전 PC 전체 CPU가 10% 이하(실제 1.7~9.8%)일 때만 시작했지만, Discord, 런처, 브라우저가 떠 있었다. 그 한도는 실행 **전**만 본다. 방 700개 `IO2` 1회차는 실행 중 PC 평균 CPU가 72.9%(다른 실행은 31~41%)로 높아 **다른 프로그램이 실행 중에 CPU를 썼을 가능성이 있고**(진행 기록의 상위 프로세스에 Unreal Editor가 나타남), 이 실행의 입력 반영 8초는 그 영향일 수 있다. 계획의 규칙(실행 전 10% 초과만 제외)을 지켜 집계에서 빼지 않았고, 700개 `IO2`의 "1/3"은 확정 결과로 읽지 않는다. 방 400개 `IO0` 3회차(PC 평균 38%)와 `IO1` 3회차(49%)도 PC 부하가 높았다. 그래서 **방 400개의 `IO0`/`IO1` 실패는 PC 부하와 섞였을 수 있다.** 반대로 방 500개와 600개는 PC 평균이 23~36%였고 3회가 모두 같은 방향이라 결론이 흔들리지 않는다.
- **`IO4`의 상한을 찾지 못했다.** 사전 규칙이 700개까지만 허용했다. 더 큰 방 수는 새 계획을 세워 재야 한다. 부하 생성기(4스레드)도 같은 PC의 코어를 쓰므로 생성기 쪽 한계(스레드당 CPU 27%)가 먼저 올 수도 있다.
- **루프백이라 송신 시스템 호출 비용이 실제 네트워크와 다르다.** 서버와 생성기가 코어를 나눠 쓰므로 서버 전용 기계에서는 이득이 더 클 수 있다.
- **`IO1`이 보인 "느려진 연결의 지연 누적"은 고치지 않았다.** 입출력이 밀리면 논리 스레드가 이미 낡은 스냅샷을 계속 큐에 쌓는다. 스냅샷은 마지막 상태만 의미가 있으므로, 연결의 송신 큐가 깊을 때 새 스냅샷으로 대체하거나 건너뛰는 처리가 필요하다(후속 설계 후보).
- 정확성은 시험으로 확인했지만(통합 테스트 전체를 입출력 스레드 4개로 반복, 변형 3가지를 시험이 잡음, 소멸 순서 결함 수정) **기본값은 여전히 `--io-threads 0`이다.** 기본값을 바꾸려면 스레드 수 선택과 위의 느린 연결 처리까지 정해야 한다.
- Windows, Release, 이 PC 한 대의 결과다. Linux 결과는 없다.
