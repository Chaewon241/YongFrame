# 게임 워크로드 부하 측정

- **질문:** 방당 4명이 입력을 보내고 서버가 초당 20번 스냅샷을 돌려주는 부하에서, 서버(`io_context` 스레드 1개)는 방 몇 개(몇 명)까지 틱을 정시에 처리하는가.
- **계획과 합격 기준:** [docs/stage4.md](../../docs/stage4.md)의 "부하 측정 계획"(측정 전에 작성). 3단계의 방법(열린 루프, 생성기 포화 감지, 조건당 3회, 한 번에 한 변수)을 따른다.
- **바꾼 변수:** 방 수 하나(25, 50, 100, 200, 300, 400, 그리고 500, 600, 700). **고정한 것:** Release 빌드(MSVC 14.44, VS 2022), 서버 `--log-level info --stats-interval 1`, `io_context` 스레드 1개, `TCP_NODELAY` 켬, 인메모리, `PlayConfig` 기본값(맵 5,000 x 5,000 cm, 300 cm/s, 20Hz, 방당 4명), 플레이어당 `MoveInput` 10Hz(무작위 방향, 10%는 정지), 워밍업 5초, 측정 30초, 매 실행 새 서버 프로세스, 생성기 `--threads 4`.
- **환경:** `raw/game-load-environment.txt`. Ryzen 5 5600(6코어 12스레드), RAM 16 GB, Windows 11, **같은 PC 루프백**. 서버는 커밋 `57c2a1f`의 Release 빌드이고 부하 생성기는 같은 작업 폴더에서 빌드했다(생성기 소스는 이 결과와 같은 커밋에 들어 있다). 측정 중 Chrome과 Discord가 실행 중이었다.
- **조건 추가에 대한 기록:** 1차는 25~400개 방으로 계획했다. 전부 합격해 한계가 보이지 않아, 결과를 본 뒤 **500, 600, 700개를 추가**했다(2차). 합격 기준은 바꾸지 않았다.
- **원본:** `raw/game-load.csv`(1차 18회), `raw/game-load-extra.csv`(2차 9회), 실행별 화면 출력 `raw/game-r<방>-rep<회차>.txt`, 서버 로그 `raw/game-server-*.log.gz`(손실 없이 gzip 압축, 원본은 연결/종료 줄이 많아 용량이 큼), 실행 직전 전체 CPU `raw/game-load-background.txt`, `raw/game-load-extra-background.txt`. 표는 `aggregate.py`(`python results/stage4/aggregate.py game-load.csv`)로 다시 만들 수 있다.

## 해석

1. **이 구성에서 합격 기준을 3회 모두 통과한 최대 방 수는 500개(플레이어 2,000명)다.** 방 500개에서 서버 CPU는 약 86%이고, 도착 간격 p99는 53 ms, 입력 반영 p99는 83 ms였다. 600개부터는 서버 CPU가 98% 안팎에 붙어 한계에 닿는다. 한계는 500개와 600개 사이에 있으며 정확한 값은 재지 않았다.
2. **서버 CPU는 방 수에 비례하고 방 하나는 코어의 약 0.17~0.21%다.** 25개 방은 0.29%로 높게 나오는데 CPU 사용 시간이 작아 상대 오차가 큰 것으로 보인다. 선형이라면 이 PC에서 100%에 닿는 지점은 약 550~600개이며 실측(600개에서 98%)과 맞는다.
3. **한계를 넘으면 서버가 시뮬레이션 시간은 지키고 스냅샷이 줄어든다.** 600개 이상에서 서버가 처리한 틱 수는 약 585~618개(30초 x 20Hz = 600)로 거의 그대로인데, 클라이언트가 받는 스냅샷은 4~28%가 누락되고 도착 간격의 중앙값이 50 ms에서 52~63 ms로 늘었다. 서버가 늦으면 밀린 틱을 한 번에 최대 3개까지 따라잡고 스냅샷은 마지막 상태 하나만 보내기 때문이다(설계한 동작, [stage4.md](../../docs/stage4.md)). 그래서 위치 계산은 현실 시간을 따라가지만 화면 갱신이 거칠어진다. 정합성 위반은 과부하에서도 0건이었다.
4. **입력 반영 지연의 중앙값은 방이 늘수록 커진다**(25개 29 ms에서 500개 45 ms). 틱 간격의 절반(25 ms)이 기본이고, 한 틱의 처리와 전송에 걸리는 시간이 더해진다.
5. **측정 종료 뒤 연결을 한꺼번에 닫으면 서버가 틱을 건너뛴다.** 측정 직후 생성기가 연결 1,200~2,800개를 RST로 닫는 동안 서버가 150 ms 이상 밀려 틱이 2~11개 건너뛰어졌다(`skipped_with_teardown`, 300개 방부터). 측정 구간 안에서는 0건이므로 이번 합격 판정과 무관하지만, 서버 종료나 장애로 연결이 몰려 끊기는 상황의 특성으로 기록해 둔다. 원인(방 정리와 알림 처리 중 무엇이 느린지)은 따로 분석하지 않았다.

## 알려진 문제와 한계

- **집계의 구간 경계를 고친 기록:** 처음에는 서버 틱 건너뜀을 "측정 종료 **이후** 첫 통계 줄"까지의 증가분으로 계산했다. 그랬더니 300~400개 방에서 2~9건이 나와 합격 기준(0.1%)을 넘는 것처럼 보였지만, 클라이언트가 본 최대 간격(62~85 ms)과 맞지 않았다. 확인해 보니 생성기가 연결을 닫는 정리 구간이 섞여 있어서, 측정 종료 **이전** 마지막 줄까지로 고쳤다. 합격 기준은 그대로이고 정리 구간 값은 위 5번에 따로 적었다. 이 수정은 결과를 본 뒤에 했지만 원인이 확인된 집계 오류의 수정이다.
- **원인을 모르는 한 번의 정체:** 방 400개 3회차에서 클라이언트 1,600명이 동시에 스냅샷 하나를 놓쳤고 최대 도착 간격이 148.7 ms였다(서버 로그의 최대 틱 처리 93 ms와 같은 시점으로 보임). p99 기준으로는 합격이다. 배경 프로그램, 윈도우 스케줄러, 서버 내부 중 무엇인지 확인하지 못했다.
- **배경 부하:** 실행 직전 전체 CPU는 대부분 0~36%였지만 일부는 높았다(300개 2회차 49, 93%, 700개 1회차 85, 28%). 측정 구간에 영향을 줬는지는 알 수 없다. 서버 한계(500개와 600개 사이)가 3회 모두에서 같은 쪽으로 나온 점은 결과의 신뢰를 높여 주지만 정확한 경계값은 아니다.
- **같은 PC의 루프백이다.** 서버와 생성기가 CPU를 나눠 쓰고, 실제 네트워크의 지연과 대역폭 제한이 없다. 서로 다른 머신에서 재지 않았다. 최대 수신 대역폭은 약 3.4 MiB/s(방 600개)로 루프백에서는 문제가 아니지만 실제 회선에서는 달라진다.
- **워크로드는 가정이다.** 입력 10Hz, 방당 4명 전원 접속, 모두 계속 움직이는 상황을 가정했다. 실제 게임은 입력이 변할 때만 보내고 가만히 있는 시간이 길 수 있어 더 가볍거나, 방 안에서 다른 메시지(채팅 등)가 섞여 더 무거울 수 있다. 4단계 서버에는 채팅 외 다른 게임 메시지가 없다.
- 조건당 3회라 간헐적인 정체를 통계적으로 다루기에는 적다. Windows, Release, 이 PC 한 대의 결과이며 Linux 결과는 없다.
- 서버 CPU는 프로세스 전체 값이고, 스냅샷 직렬화, 송신, 계산 중 무엇이 큰지는 분해하지 않았다(최적화는 하지 않았다).

## 결정

- 서버 구성(스레드 1개, 틱 20Hz)의 **최대 안정 규모를 방 500개(플레이어 2,000명)로 기록한다.** 이 구성에서 동시 접속자 수 목표가 이보다 낮다면(게임 기획은 방당 최대 4명, 방 수 미정) 현재 구조로 충분하다.
- 스레드 수를 늘리는 비교 실험(3단계 실험 3)의 병목 증거가 하나 더 생겼다. 한계에서 서버 CPU가 한 코어에 붙는다. 다만 이 서버의 틱은 한 스레드에서 방들을 순회하므로 스레드를 늘리려면 방 단위로 나누는 설계가 필요하다. 지금은 하지 않는다.
- 스냅샷을 수신자마다 따로 직렬화하는 비용(방당 4번)은 병목 증거가 없어 그대로 둔다. 필요해지면 먼저 이 비용을 분해해 측정한다.
