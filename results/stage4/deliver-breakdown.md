# 서버 틱 시간 분해와 Deliver 비용 (병목 증거)

- **질문:** 서버 CPU는 어디에 쓰이는가. 방 500개 근처에서 서버가 한 코어에 붙는 이유는 무엇이고, 무엇을 고치면 방 수를 늘릴 수 있는가.
- **한 번에 한 변수:** 아래 (1)은 서버 틱을 단계별로 시간 재서 본 것(코드를 바꾸지 않은 계측), (2)는 같은 세션에서 속도와 충돌을 되돌린 비교, (3)은 Deliver 한 번의 비용을 서버 밖에서 따로 잰 마이크로벤치다.
- **계획:** [docs/stage4.md](../../docs/stage4.md)의 "방당 CPU 증가 원인 분해 실험 계획"(측정 전에 작성).

## (1) 틱 시간의 단계별 분해 (방 400개, 12회 실행의 중앙값)

서버 틱 안에서 이동 계산, 재생/완공 갱신, 메시지 구성, 전송(Deliver)의 시간을 재서 서버 통계 줄에 누적했다. 값은 서버 CPU가 약 61%일 때의 **ms/s**(1초당 몇 ms를 쓰는가)다.

| 단계 | ms/s | 틱 시간 중 비율 |
| --- | ---: | ---: |
| 이동 계산 (World::Step) | 3.9 | 0.7% |
| 재생/완공 갱신 | 1.1 | 0.2% |
| 메시지 구성 (수신자 목록, 스냅샷) | 6.3 | 1.2% |
| **전송 (Deliver)** | **532.7** | **97.9%** |
| 틱 합 | 544.3 | 100% |
| 틱 밖 (수신, 완료 처리 등) | 약 60 | |

**서버 시간의 약 98%는 `Deliver`다.** 틱 한 번에 전송은 약 26.6 ms이고, 플레이어 1,600명에게 보내므로 한 번 보내는 데 약 16.6 µs가 든다. 이동 계산, 갱신, 구성은 합쳐 1~2%라서 이 부분을 최적화해도 방 수는 거의 늘지 않는다.

## (2) 속도와 충돌은 CPU를 바꾸지 않았다 (방 400개, 같은 세션에서 번갈아 3회씩)

| 조건 | 서버 CPU 중앙값 (최소~최대) | 이동 계산 µs/틱 |
| --- | --- | ---: |
| X0 속도 360, 충돌 켬 (새 서버 그대로) | 60.7% (58.7~62.6) | 196 |
| X1 속도 300 | 61.9% (56.4~63.8) | 188 |
| X2 충돌 끔 | 61.1% (56.5~84.4) | 43 |
| X3 속도 300, 충돌 끔 | 63.5% (60.3~84.1) | 46 |

판정 규칙(3%포인트 이상 낮아야 기여)을 만족하는 조건이 없다. **속도와 충돌은 방당 CPU 증가의 원인이 아니다.** 충돌은 이동 계산을 틱당 약 150 µs(방 전체) 늘리지만 전체 틱 시간의 0.5% 안팎이다. X2, X3의 3회차(84%)는 두 번 모두 마지막 라운드의 실행이며, 이 세션 중에 PC의 다른 프로그램이 CPU를 쓴 것으로 보이고 확인하지 못했다.

**같은 서버가 세션마다 달랐다:** 같은 새 서버의 방 400개 CPU가 이 세션에서는 60.7%, 앞선 재측정에서는 84.3%, 이전 측정(충돌 이전)은 70.7%였다. 이 편차(20% 넘게)가 코드 변경의 효과보다 크다. 그래서 "충돌 이후 방당 CPU가 15~27% 늘었다"는 결론을 철회했다([game-load-recheck.md](game-load-recheck.md)의 "정정").

## (3) Deliver 한 번의 비용 분해 (`bench_deliver`, 서버 없이 한 프로세스에서)

스냅샷은 서버가 보내는 것과 같은 모양(플레이어 4명, 본문 72 B, 프레임 78 B)이고 200,000회 반복, 세 번 실행했다.

| 항목 | 한 번당 | 비고 |
| --- | ---: | --- |
| 직렬화 (`SerializeToArray`) | 약 0.06 µs | |
| 프레임 인코딩 (`EncodeFrame`, vector 할당 포함) | 약 0.04~0.07 µs | |
| **송신 (`async_write` 연쇄, 완료 처리 포함)** | **약 13.7~14.2 µs** | 루프백 TCP, 다른 스레드가 읽어 비움 |
| 송신 (`write` 시스템 호출만) | 약 17.3~17.6 µs | |

세 번의 실행이 거의 같았다(송신 13.7~14.2 µs). **직렬화와 프레임 인코딩은 송신의 1% 미만이다.** 서버에서 잰 전송 한 번의 비용(약 16.6 µs)이 이 벤치의 송신 비용(14~17.6 µs)과 일치한다. 즉 **Deliver의 비용은 소켓 송신 시스템 호출이다.**

## 해석과 결론

1. **병목은 송신 시스템 호출이다.** 방 500개는 초당 플레이어 2,000명 x 20번 = 40,000번의 송신이고, 한 번에 약 14~17 µs면 서버 한 코어의 약 56~70%다. 틱의 나머지(이동, 구성)와 수신 처리까지 더하면 한 코어가 차는 지점이 방 450~500개 근처다.
2. **버려도 되는 후보(증거 있음):** 직렬화를 방 단위로 한 번만 하기, 메시지 객체 풀, 이동 계산 최적화, 충돌 검색(격자 분할)은 각각 전체의 1% 안팎이라 방 수를 늘리지 못한다. 하지 않는다.
3. **한계(중요):** 이 PC는 **같은 PC의 루프백**이라 송신 시스템 호출 안에서 수신 쪽 TCP 처리까지 일부 같이 일어난다. 실제 네트워크에서는 송신 비용이 더 작을 수 있다. 이 결과는 "이 구성에서 한 코어가 송신으로 차는 한계"의 증거이고, 실제 배포에서의 비용은 아니다.
4. 배경 프로그램이 CPU를 쓰는 중에 잰 숫자다(전체 CPU 34~68%). 송신 시간은 세 번의 실행이 거의 같았다.

## 개선 후보 (가설이며 아직 측정하지 않았다)

| 후보 | 기대 | 비용과 위험 |
| --- | --- | --- |
| **A. 송신을 일꾼 스레드로 넘기기**(게임 로직은 한 스레드, 소켓 송신은 연결별 strand로 여러 스레드) | 송신 시스템 호출을 여러 코어가 나눠 한다. 틱 스레드는 메시지를 한 번 직렬화해 각 연결에 넘기기만 해서 틱 시간이 크게 줄 수 있다. 같은 PC에서는 생성기와 코어를 나눠 써서 이득이 줄어든다. | `Session`의 송신 큐와 종료 처리를 strand로 보호해야 한다. 3단계 실험 3(스레드 수)과 같은 방향이다. |
| B. 변하지 않은 스냅샷은 보내지 않기 | 가만히 있는 플레이어가 많은 실제 게임에서 송신 수가 줄어든다. 이 부하(플레이어 대부분이 계속 움직임)에서는 이득이 없다. | 클라이언트 보간과의 상호작용, "방 전체가 멈춤" 판정. |
| C. 스냅샷 주기를 20 Hz에서 10 Hz로 | 송신이 절반이 된다. | 조작감과 보간 지연이 달라지는 설계 결정이다. 사용자가 정할 일이다. |
| D. 한 연결에 쌓인 여러 프레임을 한 번에 쓰기(scatter-gather) | 틱당 메시지가 둘 이상일 때만 의미가 있다(스냅샷 하나가 보통이라 이득이 작다). | 작다. |

## 알려진 한계

- 서버 측 계측(1)(2)는 CPU가 61% 근처인 방 400개에서 잰 것이다. 500개 부근(포화)에서 비율이 같은지는 재지 않았다.
- (2)는 PC에서 다른 프로그램이 일부 실행 중일 때 쟀고(실행 전 CPU 17%) 마지막 라운드에 한 번씩 이상치(84%)가 있었다.
- 같은 PC의 루프백, Windows, Release, 이 PC 한 대의 결과다. Linux 결과는 없다.
