# 확장 측정 (다중 스레드 부하 생성기, Active 2,000~10,000)

- **질문:** 기준 측정에서 부하 생성기가 먼저 포화되어 판정하지 못한 Active 5,000 이상을 생성기를 다중 스레드로 바꿔 다시 재면, 서버(`io_context` 스레드 1개)는 어디까지 합격하는가.
- **빌드와 환경:** Release(MSVC 14.44, VS 2022). 커밋과 작업 폴더 상태, CPU/RAM은 `raw/scaled-environment.txt`. 서버와 생성기는 **같은 PC**의 루프백이다(Ryzen 5 5600, 6코어 12스레드, RAM 16 GB, Windows 11).
- **서버 설정(기준과 동일):** 로그 `info`, `TCP_NODELAY` 켬, `io_context` 스레드 1개, 인메모리 저장소. 매 실행 새 서버 프로세스.
- **워크로드:** Active(연결당 초당 10건), payload 64바이트, 워밍업 5초(기록 안 함), 측정 30초. 조건당 3회.
- **바꾼 것:** 부하 생성기를 스레드 1개에서 **여러 스레드**(`--threads`)로 바꿨다. 연결 수 2,000(생성기 1스레드와 4스레드), 3,000, 4,000, 5,000, 7,500, 10,000(모두 4스레드).
- **바꾸지 않은 것:** 합격 기준 전부(연결 성공률, 오류율, p99 50 ms, 메모리 1.05배). 생성기 포화 판정만 스레드가 여러 개가 되었으므로 "생성기 **스레드당** 평균 CPU 80% 이하"로 적용했다(스케줄 지연 p99 5 ms 이하는 그대로). 80% 규칙의 의미는 같고 단위만 스레드 수에 맞춘 것이다.
- **원본:** `raw/scaled.csv`(21회), 실행별 출력 `raw/scaled-active-<연결수>-t<스레드>-r<회차>.txt`, 진행 기록 `raw/scaled-progress.txt`.

## 결과

값은 3회의 **중앙값**, 괄호는 최솟값~최댓값이다. 지연은 ms, 서버 CPU는 한 코어 기준 %, 생성기 CPU는 스레드당 %다. 모든 실행에서 **연결 성공률 100%, 중간에 끊어진 연결 0, 응답 불일치 0**이었다. 생성기 스케줄 지연 p99는 모든 실행에서 1.5~1.9 ms였고 생성기 스레드당 CPU는 최대 56%라서 **포화 판정은 한 번도 나오지 않았다**(생성기가 한계가 아니었다).

불합격 사유: 5,000은 p99가 50 ms를 넘은 두 번(60.7, 89.4 ms). 7,500과 10,000은 서버가 요청을 따라가지 못해 응답이 쌓이고(p50이 9~14초, 측정 끝에 응답 못 받은 요청이 수십만~백만 건), 서버 메모리가 계속 늘었다(후반/전반 1.7~1.9배). 이 두 구간의 지연 수치는 처리 한계를 넘긴 **과부하 상태의 값**이다.

## 해석

1. **서버의 한계가 처음으로 보였다.** Active 3,000연결(초당 3만 건)까지는 p99가 1~4 ms로 안정적이고 4,000연결(초당 4만 건)은 합격 기준을 3번 모두 통과한다. 5,000연결(초당 5만 건)에서 기준을 안정적으로 지키지 못하고, 7,500연결부터는 과부하다. 이 구성에서 **합격 기준을 3회 모두 통과한 최대 연결 수는 Active 4,000**이다.
2. **7,500 이상의 병목은 서버의 스레드 1개다.** 서버 CPU가 99%에 붙고 처리량이 오히려 줄었다(7,500: 약 45,100/s, 10,000: 약 39,100/s). 생성기는 스레드당 44~56%로 여유가 있었고 스케줄 지연도 정상이었으므로 기준 측정의 "생성기 한계"와는 다르다. 서버가 소화하는 최대 처리량은 **초당 약 4만 5천 건**으로 관측되었다. 기준 측정 때 낸 추정(5만 건 안팎)과 같은 자릿수다.
3. **기준을 넘기기 전부터 꼬리 지연이 불안정해진다.** 4,000과 5,000에서 같은 조건의 p99가 1.5 ms와 30 ms, 3.6 ms와 89 ms로 반복마다 크게 갈렸다(평균은 거의 같다). 서버 CPU가 80~90%인 구간에서 가끔 수십 ms의 정체가 생기는 것으로 보이지만, 정체의 **원인은 확인하지 못했다**(같은 PC의 다른 프로세스, 윈도우 스케줄러, 서버 내부 모두 가능). 원인을 찾으려면 따로 실험해야 한다.
4. **연결당 메모리는 기준과 같다.** 4,000~5,000연결에서 서버 메모리는 연결 1,000개당 약 10 MB(5,000연결에서 58 MB)로 Idle과 일치한다.
5. **다리 측정(생성기 1스레드 vs 4스레드, 2,000연결):** 처리량과 오류는 같다(2만/s, 오류 0). p99는 0.57 ms와 0.49 ms로 생성기 구성 때문에 차이가 나지 않는다. 다만 **서버 CPU가 기준 측정(39.3%)과 이번 세션(24~48%)에서 달랐다.** 같은 조건에서도 서버 CPU는 실행마다 변동이 크므로(이번 4스레드 2,000연결 3회가 31, 31, 48%), 서버 CPU의 작은 차이는 의미 있는 차이로 읽지 않는다. 응답 1건당 CPU 시간 "약 20 µs"는 기준 측정의 값이며 이번에는 4,000연결 약 22 µs, 5,000연결 약 16 µs로 일정하지 않았다(원인 미확인: 부하가 높을수록 한 번 깨어날 때 처리하는 건수가 늘어서일 수 있다는 것은 추측이다).

## 한계

- 같은 PC의 루프백이라 서버와 생성기가 CPU를 나눠 쓴다. 생성기 스레드 4개가 서버와 같은 CPU(12스레드)를 쓴 결과이며, 다른 머신에서 재면 숫자가 달라질 수 있다.
- 합격 기준은 연결 수별로 4,000(합격 3/3)과 5,000(합격 1/3)만 구분했다. 4,000과 5,000 사이는 재지 않았다. 4,000에서 p99 30 ms 실행이 2번 있었으므로 "4,000이 여유 있게 안정적"이라고 말할 수 없다.
- 반복은 조건당 3회라 꼬리 지연의 간헐적 정체를 통계적으로 다루기에는 적다.
- 연결 수 10,000까지만 시도했다(윈도우 임시 포트 약 16,000개 제한). Windows, Release, 이 PC 한 대의 결과이며 Linux 결과는 없다.
- 서버 CPU는 프로세스 전체 값이며 코드별 분해는 하지 않았다.

## 결정

- 기준 구성의 **Active 최대 안정 연결 수는 4,000**(초당 4만 건)으로 기록한다. 서버가 소화하는 처리량의 상한은 초당 약 4만 5천 건으로 관측되었다.
- 부하 생성기는 더 강화하지 않는다. 생성기는 서버보다 먼저 포화되지 않았다.
- 다음은 비교 실험이다. 병목이 서버의 스레드 1개 처리량임이 보였으므로 실험 3(스레드 수)의 가치가 커졌다. 순서는 실험 1(로그 레벨), 실험 2(`TCP_NODELAY`) 다음 실험 3이다.
