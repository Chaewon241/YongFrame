# 기준 측정 (baseline)

- **질문:** 기준 구성(로그 `info`, `TCP_NODELAY` 켬, `io_context` 스레드 1개, 인메모리 저장소)의 서버가 Idle과 Active 워크로드에서 연결 수 100~10,000 구간을 [합격 기준](../../docs/stage3.md#합격-기준-측정-전에-확정)으로 판정하면 어떻게 나오는가.
- **커밋과 빌드 설정:** Release 빌드(MSVC 14.44, VS 2022). 커밋과 작업 폴더 상태는 `raw/environment.txt`에 있다.
- **서버/부하 생성기 환경:** `raw/environment.txt`. AMD Ryzen 5 5600(6코어 12스레드), RAM 16 GB, Windows 11. 서버와 부하 생성기가 **같은 PC**에서 루프백으로 통신한다.
- **워크로드:** Active는 연결당 초당 10건, Idle은 5초마다 1건. payload 64바이트. 워밍업 5초(기록 안 함), 측정 30초. 연결 수 100, 500, 1,000, 2,000, 5,000, 10,000. 조건당 3회 반복, 매 실행 새 서버 프로세스.
- **고정한 변수:** 서버 설정, 빌드, payload, 시간. **바꾼 변수:** 연결 수와 워크로드(Idle/Active).
- **합격 기준(측정 전에 작성):** 연결 성공률 99.9% 이상, 오류율 0.1% 이하, p99 왕복 지연 50 ms 이하, 서버 메모리 후반/전반 1.05배 이하, 생성기 포화 아님(스케줄 지연 p99 5 ms 이하, 생성기 CPU 80% 이하).
- **반복별 원본 결과 위치:** `raw/baseline.csv`(36회), 실행별 화면 출력 `raw/baseline-<워크로드>-<연결수>-r<회차>.txt`, 도구 수정 후 재측정 `raw/baseline-rerun.csv`(6회)와 `raw/baseline-rerun-*.txt`.

## 결과

값은 3회의 **중앙값**이고, 괄호는 최솟값~최댓값이다. 지연은 밀리초(ms), 서버 CPU는 한 코어 기준 %, 서버 메모리는 측정 끝의 작업 집합(MB)이다. 모든 실행에서 **연결 성공률은 100%, 오류율은 0%** 였다(불일치, 응답 없음, 전송 오류가 한 건도 없음).

원측정에서 Idle 500(3회)과 Idle 10,000(1회)이 "생성기 포화"로 표시되었지만 생성기 CPU는 0.4~6.4%였다. 포화가 아니라 **타이머 해상도 문제**(스케줄 지연이 윈도우 기본 타이머 간격인 약 15ms로 찍힘)로, 도구의 문제였다. 같은 구간에서 지연 p99는 0.22 ms로 정상이었다. 원래 결과는 지우지 않고 남겼으며, 도구를 고친 뒤 이 두 조건을 다시 측정한 6회는 모두 스케줄 지연 1.5~1.8 ms로 합격했다. (아래 "한계" 참고)

## 해석

1. **Active 2,000연결(초당 2만 건)까지는 기준을 모두 통과한다.** p99 왕복 지연 0.76 ms, 오류 0, 메모리 안정(후반/전반 0.999배). 서버 스레드 1개가 한 코어의 39%를 쓴다.
2. **Active 5,000 이상에서는 서버가 아니라 부하 생성기가 먼저 한계에 닿았다.** 그래서 이 서버의 최대 안정 연결 수는 **"Active 기준 2,000 이상, 상한은 아직 모름"** 이다. "몇 명까지"라는 답은 생성기를 강화한 뒤에 낼 수 있다.
3. **응답 1건당 서버 CPU 시간은 약 20 µs** 다(500~2,000연결: 21.6, 20.6, 19.6 µs). 이 값이 계속 유지된다면 스레드 1개의 한계는 초당 5만 건 안팎일 것으로 **추정**된다. 5,000/10,000에서 서버 CPU가 79~80%였던 것과 모순되지 않지만, 생성기가 포화였으므로 **검증된 값이 아니다.**
4. **Idle은 10,000연결까지 모두 합격이다.** 연결을 유지하는 비용은 CPU 5% 이하, 메모리는 **연결 하나당 약 10.2 KB**(1,000/5,000/10,000에서 모두 같음)로 선형이다. 읽기 버퍼가 연결마다 8 KiB(`Session::kReadBufferSize`)라서 그 비중이 클 것이라는 **가설**이 있다. 확인은 읽기 버퍼 크기를 바꿔 측정해야 한다. 지금은 가설이다.
5. **지연과 메모리 모두 안정적이다.** 어느 조건에서도 메모리가 계속 늘지 않았다(최대 1.011배).

## 한계

- 서버와 생성기가 같은 PC의 루프백이다. 두 프로세스가 CPU를 나눠 쓰므로 실제 네트워크에서의 지연과 다르다. 서로 다른 머신에서 재지 않았다.
- 부하 생성기는 스레드 1개다. Active 5,000 이상의 서버 한계는 이 도구로는 잴 수 없다.
- 연결 10,000개까지만 시도했다(윈도우 임시 포트 약 16,000개 제한).
- Windows, Release 빌드, 이 PC 한 대의 결과다. Linux 결과는 없고, 다른 PC에서는 숫자가 달라질 수 있다.
- 반복은 조건당 3회다. 간헐적인 이상을 배제하기에는 적다.
- 윈도우 11에서 타이머 해상도 요청이 일부 실행에서 무시되는 것으로 의심되지만, **원인은 증명하지 못했다.** 같은 조건을 이후 짧게 재현했을 때는 문제가 나타나지 않았다. 도구에 해상도 요청을 무시하지 않게 하는 설정을 추가해 재측정했을 뿐이다.
- 서버 CPU와 메모리는 프로세스 전체 값이다. 어느 코드가 얼마를 쓰는지는 분해하지 않았다.

## 결정

- 이 구성과 결과를 **기준(baseline)** 으로 채택한다. 이후 비교 실험은 같은 도구, 같은 절차로 한 변수씩 바꿔 이 값과 비교한다.
- Active 5,000 이상은 **부하 생성기를 강화한 뒤 다시 잰다.** 다음 작업: 생성기가 여러 스레드(또는 프로세스)로 일을 나눠 서버보다 먼저 포화되지 않게 한다.
- 합격 기준은 바꾸지 않는다.
