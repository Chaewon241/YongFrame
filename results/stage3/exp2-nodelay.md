# 실험 2: TCP_NODELAY (Nagle 알고리즘 켬/끔)

- **질문:** 서버 소켓의 `TCP_NODELAY`를 끄면(Nagle 알고리즘 동작) 지연과 처리량이 켠 상태(기준)와 달라지는가.
- **계획과 판정 기준:** [docs/stage3.md](../../docs/stage3.md)의 "실험 2 계획"(측정 전에 작성). 지표(p50, p99, 서버 CPU, 처리량)별로 `off`의 중앙값이 `on` 3회의 최솟값~최댓값 범위 밖이면 차이가 있다고 본다. 결정 규칙: `off`가 p99를 낮추는 방향으로 기준을 넘고 나머지가 나빠지지 않을 때만 기본값 변경을 검토한다.
- **바꾼 변수:** 서버 `--tcp-nodelay on|off` 하나(서버가 `nodelay=off`로 시작하는 것을 로그로 확인했다). 부하 생성기 소켓은 항상 `TCP_NODELAY`를 켰다. **고정한 것:** Release 빌드(MSVC 14.44, VS 2022), 로그 `info`, `io_context` 스레드 1개, 인메모리 저장소, 생성기 `--threads 4`, payload 64B, 워밍업 5초, 측정 30초, 매 실행 새 서버 프로세스.
- **워크로드:** A는 기준 Active(연결당 초당 10건)로 연결 1,000 / 2,000. B는 이 실험에서만 쓰는 추가 워크로드(연결당 초당 **100**건)로 연결 100 / 200(초당 1만 / 2만 건). 조건당 3회, 두 설정을 번갈아 실행(1, 3회차 `on` 먼저, 2회차 `off` 먼저), 같은 세션에서 `on`도 다시 쟀다.
- **환경:** `raw/exp2-environment.txt`. Ryzen 5 5600(6코어 12스레드), RAM 16 GB, Windows 11, **같은 PC 루프백**. 측정 중 Discord가 켜져 있었다(거의 유휴). 실행 직전 전체 CPU 사용률은 대부분 0~18%였지만 24회 중 6회(`off` 5회, `on` 1회)에서 20~42%가 한 번 이상 찍혔다(`raw/exp2-background-cpu.txt`).
- **원본:** `raw/exp2-nodelay.csv`(24회), 실행별 `raw/exp2-nodelay*-*.txt`, `raw/exp2-background-cpu.txt`.

## 결과

값은 3회의 **중앙값**이고 괄호는 최솟값~최댓값이다. 지연은 ms, 서버 CPU는 한 코어 기준 %다. 24회 모두 **합격**이었고(연결 성공률 100%, 오류 0, 불일치 0) 처리량은 모든 조건에서 목표값과 같았다(1만 / 2만 건/초).

## 해석

1. **`TCP_NODELAY`를 끄는 것이 지연을 줄이지 않았다.** 결정 규칙의 조건(`off`가 p99를 낮춤)을 어느 조건에서도 만족하지 못했다. 그러므로 기준 설정(`on`)을 유지한다.
2. **차이는 있어도 아주 작다.** 사전에 정한 기준(중앙값이 상대 범위 밖)으로 엄밀하게 보면 세 곳이 걸린다. B 100연결의 p50(`off` 0.116 vs `on` 최댓값 0.113, 차이 약 0.006 ms), B 200연결의 p99(0.582 vs 최댓값 0.580, 0.002 ms 초과), B 200연결의 서버 CPU(41.7% vs 최댓값 40.5%, 약 +2%p). 모두 `off`가 같거나 약간 **나쁜** 방향이고 크기가 마이크로초 단위이거나 CPU 몇 %p 수준이다. A 워크로드(연결당 10건/초)에서는 기준에 걸린 항목이 없다. 3회 반복으로는 이 정도 크기를 확정하기에는 표본이 적다.
3. **Nagle의 영향이 거의 드러나지 않은 이유(미확인 추정):** 한 연결의 요청 간격이 10 ms 이상이어서 서버가 응답을 보낼 때 앞선 응답은 이미 ACK된 상태라 Nagle이 기다릴 이유가 없었던 것으로 짐작한다. 루프백은 ACK도 매우 빠르다. 이 추정은 확인하지 않았다(패킷을 직접 관찰하지 않았다). 한 연결에서 응답을 연달아 여러 개 보내는 워크로드(예: 방 전체 스냅샷을 초당 수십 번 보내는 게임)에서는 달라질 수 있어, 4단계 게임 워크로드를 만든 뒤 다시 볼 가치가 있다.

## 한계

- 같은 PC 루프백, Windows, Release, 조건당 3회다. 실제 네트워크(RTT가 큰 환경)에서는 Nagle과 지연 ACK의 상호작용이 훨씬 클 수 있는데 이 실험은 그것을 보지 않았다.
- 실행 직전 CPU 사용률에서 `off` 실행 쪽에 20~42% 순간 값이 더 많았다(`off` 5회, `on` 1회). 그 값이 측정 구간에도 영향을 줬는지는 알 수 없다. 두 설정을 번갈아 실행해 시간 순서의 편향은 줄였지만 배경 부하가 결과의 작은 차이를 만들었을 가능성을 배제하지 못한다.
- 서버만 바꿨다. 생성기 소켓의 `TCP_NODELAY`를 끈 경우는 보지 않았다.
- 연결당 응답이 연달아 나가는(배치성) 워크로드는 측정하지 않았다.

## 결정

- **서버 기본값 `TCP_NODELAY` 켬을 유지한다.** 끄는 것의 이득이 없었다.
- 다음은 실험 3(`io_context` 스레드 수 1 vs 2 vs 4, strand 적용)이다. 서버 코드 변경이 필요하고, 실험 1·확장 측정에서 서버 스레드 1개가 병목임을 확인했으므로 가장 의미 있는 비교다.
