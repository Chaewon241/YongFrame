# 4단계: 게임 서버 최소 구현 (진행 기록)

> 상태: **서버 최소 구현과 부하 측정 완료(Windows).** 방 만들기/코드 입장/이동/스냅샷/방장 변경/빈 방 삭제를 구현했고 전체 테스트가 통과했다. 부하 측정 결과 **방 500개(플레이어 2,000명)까지 합격 기준을 모두 통과**했고 600개부터 불합격이다([결과](../results/stage4/game-load.md)). 아직 Unreal 클라이언트와의 연동(게임 메시지)은 하지 않았다. 이 문서는 구현 **전에** 목표, 완료 기준, 프로토콜, 기본값을 확정했고, 구현하면서 진행 상태와 겪은 문제를 이어서 적었다. 기획은 [game-plan.md](game-plan.md), 클라이언트(Unreal) 연동 방법은 [unreal-client.md](unreal-client.md)다.

## 목표

1~4명이 **방 코드**로 같은 방에 모여, 서로의 움직임이 보이는 것. 서버가 위치를 계산하고(서버 판정), 클라이언트는 이동 **입력**만 보낸다.

## 범위

**한다 (최소 구현)**

- 방 만들기, 숫자 6자리 방 코드로 입장, 방 나가기, 최대 4명
- 방장 지정과 방장이 나가면 다음 사람에게 넘김, 빈 방 삭제
- 이동 입력(방향)을 받아 서버가 위치를 계산(속도 상한, 맵 경계), 초당 20회 방 전체 스냅샷 전송
- 연결이 끊기면 방에서 자동으로 나감
- 수동 확인용 터미널 클라이언트(`game_client`)와 자동 테스트

**하지 않는다 (확장 단계)**: 자원 채집, 집 짓기, 농사, 월드 저장, 클라이언트 예측/보정, 플레이어끼리 충돌, 장애물 충돌, 방 안 채팅(기존 채팅은 전체 방 하나로 그대로 둔다), 로그인/계정.

## 기본값 (임의로 정한 값이며 `PlayConfig` 한 곳에서 바꾼다)

사용자가 정하지 않아 **임의로 정한 기본값**이다. 서버의 이동 검증과 클라이언트 연출이 같은 값을 쓰는 것이 중요하고, 정확할 필요는 없다.

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 단위 | 센티미터 | Unreal과 같음. 서버 좌표를 클라이언트가 그대로 씀 |
| 맵 | 5,000 x 5,000 cm (50 m x 50 m) | 원점은 한쪽 모서리. 장애물 없음 |
| 이동 속도 | 360 cm/s (틱당 18 cm) | 입력은 길이 1 이하의 방향 벡터이며 서버가 길이를 1로 제한. **처음 구현과 아래의 완료 기준 검증, 부하 측정은 300 cm/s(틱당 15 cm)일 때 한 것이다.** 이후 360으로 올렸고 측정은 다시 하지 않았다 |

## 프로토콜 (`proto/game.proto`, 메시지 ID는 `src/protocol/message_ids.h`)

프레임 형식은 [protocol.md](protocol.md) 그대로다. 입력 규칙 위반과 상태 위반은 응답의 결과 코드로 알리고 연결은 유지한다. 파싱 실패, 알 수 없는 ID는 기존처럼 연결을 닫는다.

| ID | 메시지 | 방향 | 설명 |
| ---: | --- | --- | --- |
| 100 | `CreateRoomRequest{nickname}` | C→S | 방을 만들고 방장이 된다 |
| 101 | `CreateRoomResponse{result, state, wood, stone}` | S→C | 성공이면 방 코드, 내 player_id, 방 상태, 들어간 직후의 내 인벤토리(농장이면 저장된 값이 복원되어 있고 임시 방은 0) |
| 102 | `JoinRoomRequest{room_code, nickname}` | C→S | 코드로 입장 |
| 103 | `JoinRoomResponse{result, state, wood, stone}` | S→C | 성공이면 방 상태(현재 접속자 포함)와 들어간 직후의 내 인벤토리 |
| 104 | `LeaveRoomRequest{}` | C→S | 방에서 나간다 |
| 105 | `LeaveRoomResponse{result}` | S→C | |
| 106 | `MoveInput{sequence, dir_x, dir_y}` | C→S | 이동 방향(응답 없음). 방에 없으면 무시 |
| 110 | `RoomEvent{kind, player, host_player_id}` | S→C | 입장, 퇴장, 방장 변경 알림 |
| 111 | `WorldSnapshot{tick, players[{player_id, x, y, last_input_seq}]}` | S→C | 틱마다 방 전체 상태 |
| 107 | `GatherRequest{node_id}` | C→S | 자원 채집(확장 1). 규칙은 [stage4-gather.md](stage4-gather.md) |
| 108 | `GatherResponse{result, node_id, wood, stone}` | S→C | 결과 코드와 내 인벤토리 |

| 113 | `BuildRequest{structure_type, x, y}` | C→S | 집 짓기(콘텐츠 조각 1). 규칙은 [content-roadmap.md](content-roadmap.md) |
| 114 | `BuildResponse{result, structure_id, wood, stone}` | S→C | 결과 코드와 내 인벤토리 |
| 115 | `StructureUpdate{tick, structures[...]}` | S→C | 새로 생기거나 바뀐 구조물이 있는 틱에만 |

결과 코드(`GameResult`): `GAME_OK`, `GAME_INVALID_NICKNAME`(채팅과 같은 닉네임 규칙), `GAME_INVALID_ROOM_CODE`(6자리 숫자가 아님), `GAME_ROOM_NOT_FOUND`, `GAME_ROOM_FULL`, `GAME_ALREADY_IN_ROOM`, `GAME_NOT_IN_ROOM`, `GAME_NICKNAME_TAKEN`(같은 방에 같은 닉네임), `GAME_SERVER_BUSY`(방 수 상한, 코드 발급 실패). 채집 확장에서 `GAME_NODE_NOT_FOUND`(9), `GAME_NODE_DEPLETED`(10), `GAME_TOO_FAR`(11), `GAME_GATHER_COOLDOWN`(12)이 더해졌다. `RoomState`에는 `nodes`(필드 5)가 더해졌다. 건설에서 `GAME_BUILD_INVALID_TYPE`(13), `GAME_BUILD_BLOCKED`(14), `GAME_NOT_ENOUGH_RESOURCES`(15), `GAME_BUILD_TOO_FAR`(16), `GAME_STRUCTURE_LIMIT`(17)과 `RoomState.structures`(필드 6)가 더해졌다. 모두 하위 호환이다. **서버 이동에 충돌이 생겼다**(구조물과 살아 있는 노드가 플레이어를 막는다). 이동 프로토콜은 그대로이고 위치 계산만 바뀌었다.

규칙

- 한 연결은 한 번에 한 방에만 있다. 이미 방에 있으면 `GAME_ALREADY_IN_ROOM`.
- 방의 닉네임은 겹치지 않는다. 닉네임 규칙은 채팅과 같다(1~16자 등).
- `player_id`는 방 안에서 부여한 번호이며 방이 닫힐 때까지 같은 사람이면 같다. 재사용하지 않는다.
- 위치는 서버가 계산한다. `MoveInput`의 방향 길이가 1을 넘으면 1로 줄이고, NaN/무한대 값은 입력을 무시한다. 입력은 "마지막 입력이 계속 유효"하며 다음 `MoveInput`이 오기까지 같은 방향으로 이동한다. 정지는 방향 (0, 0)을 보낸다.
- `sequence`가 이전 값 이하(순서가 거꾸로이거나 중복)인 입력은 무시한다(32비트 비교). 서버는 스냅샷에 `last_input_seq`를 담아 클라이언트가 나중에 예측 보정에 쓸 수 있게 한다.
- 방장이 나가면 방에 먼저 들어온 순서로 다음 사람이 방장이 된다. 사람이 없으면 방을 지운다.
- `RoomEvent`는 입장·퇴장 때 그 사람 **본인을 뺀** 방 사람 전원에게 보낸다(입장한 본인은 응답으로 방 상태를 받는다). 방장이 바뀌면 `HOST_CHANGED`를 남은 전원에게 보낸다(나간 방장 본인은 이미 방에 없다).

## 완료 기준 (구현 전에 확정)

1. **방:** 코드로 입장, 6자리가 아니거나 없는 코드, 4명 가득 참, 중복 닉네임, 이미 방에 있음이 각각 정해진 결과 코드를 돌려준다. 방 코드는 항상 6자리 숫자이고 서로 겹치지 않는다(충돌을 일부러 만들어 재발급을 확인).
2. **방장과 정리:** 방장이 나가면 다음 사람이 방장이 되고 알림이 간다. 마지막 사람이 나가면 방이 삭제된다(방 수가 줄어듦). 연결이 갑자기 끊겨도 같다.
3. **이동:** 입력 방향대로 속도 상한 안에서 움직이고, 맵 경계 밖으로 나가지 않으며, 방향 벡터를 부풀려도(길이 1 초과) 더 빨라지지 않는다. 잘못된 입력(NaN)은 위치를 망가뜨리지 않는다. 고정 틱이라 같은 입력 열이면 같은 결과(결정적)다.
4. **동기화:** 같은 방의 두 클라이언트(실제 TCP)가 서로의 이동을 스냅샷으로 받는다. 다른 방의 사람은 받지 않는다. 방이 비면 틱이 그 방을 건드리지 않는다.
5. **견고함:** 방에 없는 연결의 `MoveInput`, 입장 전 퇴장, 연결이 끊기는 도중의 전송에서도 서버가 죽지 않는다. 틱 중에 느린 수신자 때문에 연결이 닫혀도(송신 큐 초과) 순회가 깨지지 않는다.
6. **기존 기능 유지:** 기존 테스트 121개(MySQL 11개는 비밀번호 없으면 건너뜀)가 그대로 통과한다.
7. **관측:** 방 수, 방에 있는 사람 수, 틱 수, 한 틱 처리 시간의 최댓값, 건너뛴 틱 수를 통계에 남긴다.
8. **문서:** 이 문서와 [unreal-client.md](unreal-client.md)에 Unreal 클라이언트가 쓸 프로토콜과 기준 바이트를 남긴다.

## 설계 결정

- 방 로직(`Room`, `World`)은 소켓을 모르는 순수 코드다. 연결은 기존 `ChatClient` 인터페이스(`client_id`, `Deliver`)를 그대로 쓴다. 틱과 방 관리는 `GameService`가 하고 `Server`가 소유한다.
- 서버는 여전히 `io_context` 스레드 1개다. 틱 타이머도 같은 스레드에서 돈다.
- 틱은 절대 시각으로 예약한다(`다음 시각 += 50 ms`). 처리가 밀리면 한 번에 최대 3틱만 따라잡고 나머지는 건너뛰며(건너뛴 틱 수를 통계에 기록), 따라잡은 틱마다 스냅샷을 보내지 않고 마지막 상태 한 번만 보낸다.
- 스냅샷을 보내는 중에 연결이 닫혀 방이 바뀌어도 안전하도록, 틱은 "계산 → 수신자 목록과 메시지 확보 → 전송" 순서로 나누고 전송 단계에서는 방 컨테이너를 순회하지 않는다.
- 윈도우의 기본 타이머 해상도(약 15.6 ms)에서는 50 ms 틱이 흔들릴 수 있어, 서버도 3단계에서 쓴 것과 같은 방식으로 해상도를 1 ms로 올린다(윈도우 한정).

### 테스트가 정말 버그를 잡는지 (변형 검증)

코드를 일부러 하나씩 망가뜨려 빌드하고 관련 테스트를 돌렸다. **16가지 모두 테스트가 실패해서 잡혔다**(원본 복원은 해시로 확인).

속도 상한 제거, 맵 경계 제거, NaN 검사 제거, 오래된 입력 번호 검사 제거, 방장 변경 안 함, 빈 방 삭제 안 함, 가득 참 검사 제거, 닉네임 중복 검사 제거, 방 코드 형식 검사 제거, 이미 방에 있음 검사 제거, 코드 충돌 재발급 안 함, 연결 종료 시 게임 방 정리 안 함, 입장 알림을 본인에게도 보냄, 스냅샷을 다른 방에도 보냄, 전송 중 방 컨테이너를 순회, 서버 전용 ID를 요청으로 허용.

### 터미널 시연 (`game_client`, Release 서버, 실제 20Hz 타이머)

## 부하 측정 계획 (게임 워크로드, 측정 전에 확정)

3단계의 방법([stage3.md](stage3.md): 열린 루프, 응답 대조, 생성기 포화 감지, 합격 기준을 측정 전에 확정, 조건당 3회, 한 번에 한 변수)을 게임 워크로드에 적용한다. 3단계 부하 생성기는 Ping만 보내므로 게임용 생성기 `game_load_client`를 따로 만든다.

- **질문:** 방당 4명이 입력을 보내고 서버가 초당 20번 스냅샷을 돌려주는 부하에서, 서버(`io_context` 스레드 1개)는 **방 몇 개(몇 명)까지** 틱을 정시에 처리하는가.
- **워크로드:** 방 R개, 방마다 4명(방 최대 인원). 플레이어마다 **초당 10번** `MoveInput`을 보낸다(입력마다 무작위 방향, 10%는 정지). 이동 입력 빈도 10Hz는 키보드/스틱 조작을 감안해 임의로 정한 값이다. 서버는 20Hz로 방 전체 스냅샷을 각 플레이어에게 보낸다. 워밍업 5초(기록 안 함), 측정 30초.
- **조건:** 방 수 R = 25, 50, 100, 200, 300, 400 (플레이어 100~1,600명). 조건당 3회, 매 실행 새 서버 프로세스. 바꾸는 변수는 방 수 하나다.
- **고정:** Release 빌드, 서버 `--log-level info --stats-interval 1`(틱 건너뜀 통계를 읽기 위해), `io_context` 스레드 1개, `TCP_NODELAY` 켬, 생성기 스레드 4개, 같은 PC 루프백. 방 코드/이동 규칙은 기본값(`PlayConfig`).
- **측정 항목(클라이언트가 관찰):**
  - 방 형성: 방을 만들고 4명이 모두 입장한 비율
  - 스냅샷 도착 간격(클라이언트마다 연속한 두 스냅샷 사이 시간)
  - 입력 반영 지연: `MoveInput`을 보낸 시각부터 그 `sequence` 이상이 담긴 첫 스냅샷이 도착한 시각까지
  - 누락 스냅샷: 받은 스냅샷의 틱 번호가 건너뛴 횟수(서버가 밀려 한꺼번에 처리하거나 건너뛴 틱)
  - 정합성: 스냅샷마다 방 인원이 맞는지, 위치가 유한하고 맵 안인지, 틱당 이동 거리가 서버 속도 상한(15 cm)을 넘지 않는지, 틱 번호가 증가하는지
  - 반영되지 않은 입력: 측정 구간에 보낸 입력 중 끝까지(3초 대기) 스냅샷에 반영되지 않은 것
  - 서버 CPU, 메모리, 클라이언트가 받은 스냅샷 대역폭, 서버 로그의 틱 건너뜀 증가분
- **합격 기준(모두 만족):**

| 항목 | 기준 |
| --- | --- |
| 방 형성 | 99.9% 이상(방 단위) |
| 스냅샷 도착 간격 p99 | 100 ms 이하 (틱 간격 50 ms의 2배) |
| 입력 반영 지연 p99 | 100 ms 이하 |
| 누락 스냅샷 비율 | 1% 이하 (받은 스냅샷 + 누락 분 대비 누락) |
| 서버 틱 건너뜀 | 측정 구간 틱의 0.1% 이하 (서버 로그의 통계 줄 증가분) |
| 정합성 위반 | 0건 (인원 불일치, 맵 밖/비정상 값, 이동 거리 상한 초과, 틱 역행) |
| 반영되지 않은 입력 | 0.1% 이하 |
| 끊긴 연결 | 0개 |
| 서버 메모리 | 후반 1/3 평균이 전반 1/3 평균의 1.05배 이하 |
| 생성기 포화 아님 | 스케줄 지연 p99 5 ms 이하, 생성기 스레드당 평균 CPU 80% 이하 (넘으면 판정하지 않음) |

- **추가 조건 (1차 결과를 본 뒤 추가, 기준은 그대로):** 1차(25~400개)가 모두 합격이라 서버의 한계가 보이지 않았다(400개에서 서버 CPU 약 70%). 한계를 찾기 위해 방 **500 / 600 / 700개**를 같은 절차로 추가로 잰다. 이 조건은 1차 결과를 본 뒤에 추가했다는 사실을 결과 기록에 적는다.
- **서버 틱 건너뜀의 측정 구간:** 서버 로그의 통계 줄(1초마다) 중 측정 시작 시각 이전의 마지막 줄과 측정 종료 시각 이전의 마지막 줄 사이 증가분을 쓴다. (1차 집계에서 종료 **이후** 첫 줄을 썼다가 생성기가 연결을 한꺼번에 닫는 정리 구간이 섞인 것을 발견해 고쳤다. 정리 구간의 결과는 따로 기록한다.)
- **최대 안정 방 수** = 위를 모두 만족하는 가장 큰 R(3회 모두).
- **판정하지 않는 것:** 실제 네트워크(루프백이라 지연이 짧다), Linux, 방 수가 많을 때 클라이언트 쪽 대역폭 한계. 서버 쪽 `max_tick_micros`는 실행 전체(방 만드는 구간 포함)의 최댓값이라 참고용으로만 기록하고 합격 판정에는 쓰지 않는다.

## 부하 재측정 계획 (충돌, 구역, 재생, 이동 속도 360 이후, 측정 전에 확정)

위 측정은 이동 속도 300 cm/s, 충돌이 없는 서버에서 했다. 그 뒤 **서버 이동에 충돌(구조물, 살아 있는 노드)이 들어갔고, 노드 재생 위치와 건설 구역이 생겼고, 이동 속도가 360 cm/s(틱당 18 cm)가 되었다.** 이 서버가 방 500개를 여전히 처리하는지 같은 절차로 다시 잰다([content-roadmap.md](content-roadmap.md) 완료 기준 9).

- **질문:** 새 구성의 서버(`io_context` 스레드 1개)는 위의 합격 기준으로 방 몇 개까지 합격하는가. 특히 방 500개가 여전히 3회 모두 합격하는가.
- **한 번에 한 변수가 아니다.** 충돌, 속도 360, 재생/구역 로직이 한꺼번에 바뀌었고 그 사이의 서버 커밋은 측정하지 않았다. 그래서 이 재측정은 "이전 구성 대비 새 구성 전체"를 비교할 뿐 **어느 변경이 비용을 늘렸는지는 가르지 않는다.**
- **합격 기준은 위 표 그대로다(바꾸지 않는다).** 정합성의 틱당 이동 거리 상한은 서버 속도(18 cm)로 자동 계산된다(생성기가 `PlayConfig`를 읽는다).
- **조건:** (가) 방마다 구조물 0개: 방 100 / 400 / 500 / 600개. (나) 방마다 완공된 집 20개(방당 상한, 서버 옵션 `--bench-prebuilt-structures 20`, 건설 구역 안 4줄 x 5칸, 시작 위치와 사람이 돌아다니는 중앙 줄을 비움): 방 500개. 조건당 3회, 매 실행 새 서버 프로세스.
- **추가 규칙(결과를 보기 전에 정한다):** (가) 500개가 3회 모두 합격이 아니면 (가) 300개와 450개를 더한다. (가) 600개가 3회 모두 합격하면 (가) 700개를 더한다. (나)는 추가 조건을 두지 않고 결과를 그대로 적는다.
- **고정:** Release 빌드(MSVC 14.44), 서버 `--log-level info --stats-interval 1`, `TCP_NODELAY` 켬, 생성기 `--threads 4`, 방당 4명, 플레이어당 `MoveInput` 초당 10번(입력마다 무작위 방향, 10%는 정지), 워밍업 5초, 측정 30초, 반영 대기 최대 3초, 같은 PC 루프백. 실행 도구는 `results/stage4/run-load-recheck.ps1`.
- **비교:** 같은 PC에서 이전 결과(방 500개: 서버 CPU 약 86%, 방당 0.17%, 도착 간격 p99 53 ms, 입력 반영 p99 83 ms)와 나란히 둔다. 서버 CPU(방당)의 변화를 해석에 쓴다.
- **미리 적어 두는 한계:** 생성기는 이동만 보내고 채집과 건설은 하지 않는다. 노드는 건설 구역 밖에 있고 플레이어는 중앙 주변을 무작위로 돌아다녀서 **노드와의 충돌은 거의 일어나지 않고, 비용은 "근처 장애물 추리기" 정도만 잰다.** (나)의 집은 중앙 줄을 비운 격자라 접촉은 일부만 일어난다. 채집/건설 요청이 섞인 워크로드는 재지 않는다. 같은 PC 루프백, Windows, Release, 이 PC 한 대의 결과다.

## 방당 CPU 증가 원인 분해 실험 계획 (측정 전에 확정)

재측정에서 최대 안정 방 수가 500개에서 450개로 내려갔고, 방당 서버 CPU가 약 15~27% 늘었다(방 400개: 70.7% -> 84.3%). 원인은 이동 속도 360, 이동 충돌, 재생/구역 로직, 틱에 새로 생긴 임시 객체 중 무엇인지 모른다. **원인을 모른 채 최적화하지 않는다.** 먼저 한 번에 한 변수씩 되돌려 재서 원인을 가른다.

- **질문:** 방당 CPU 증가(13.6%포인트)는 어느 변경에서 오는가.
- **서버 쪽 도구(측정 전용 옵션, 기본값은 게임 동작 그대로):** `--bench-move-speed <cm/s>`로 이동 속도를, `--bench-no-collision on`으로 이동 충돌(구조물, 노드가 막는 것)을 되돌린다. 틱을 이동 계산, 재생/완공 갱신, 메시지 구성, 전송, 합으로 나눈 누적 시간(마이크로초)을 서버 통계 줄에 더했다(`틱시간{...}`).
- **조건(방 400개 고정, 비포화 구간이라 CPU 차이가 보인다):** X0 새 서버 그대로(속도 360, 충돌 켬), X1 속도만 300, X2 충돌만 끔, X3 속도 300과 충돌 끔. 조건당 3회, 매 실행 새 서버 프로세스. 바꾸는 변수는 속도와 충돌, 두 가지뿐이고 X3은 둘을 함께 되돌린 것이다. 나머지 고정(Release, `--log-level info --stats-interval 1`, 생성기 4스레드, 워밍업 5초, 측정 30초, 반영 대기 3초)은 재측정과 같다.
- **판정 규칙(미리 정한다):** 서버 CPU 중앙값으로 비교한다. 재측정 때 같은 조건 3회의 편차가 1.7%포인트(83.5~85.2)였으므로, **X0보다 3%포인트 이상 낮으면 그 변경이 비용에 기여한 것으로 본다.** 기여 몫은 (X0 - Xk) / (X0 - 70.7)로 적는다(70.7은 이전 서버의 방 400개 CPU). 합 몫이 X0 - X3으로 설명되지 않는 나머지는 "속도와 충돌 밖의 변경(재생/구역 로직, 틱의 임시 객체)"으로 적는다.
- **단계별 시간:** 같은 실행의 서버 로그에서 측정 구간의 증가분을 틱 한 번당 마이크로초와 서버 CPU 대비 비율로 낸다. 틱 밖의 시간(수신, 완료 처리, 시스템 호출)은 "합 밖"으로 적는다.
- **판정하지 않는 것:** 합격 기준(부하 합격 판정)은 이번 실험의 목적이 아니다. 방 400개는 이미 합격이므로 판정은 참고로만 적는다. 이 실험의 결과로 코드를 바꾸지 않는다. 바꾸는 것은 다음 단계에서 증거를 보고 정한다.

## 같은 세션 이전/새 서버 비교 계획 (원인 분해에서 나온 의문을 가리기 위해, 측정 전에 확정)

원인 분해 실험(조건 X0~X3)에서 속도와 충돌을 되돌려도 서버 CPU가 변하지 않았다(모두 61~64%). 그런데 같은 새 서버의 방 400개 CPU가 이번 세션에서 60.7%이고 지난 재측정에서는 84.3%였다. **세션마다 20% 넘게 달라질 수 있다면 "이전 측정과 비교해 방당 CPU가 15~27% 늘었다"는 결론이 코드 때문이 아니라 측정한 날의 PC 상태 때문일 수 있다.**

- **질문:** 이전 서버와 새 서버를 **같은 세션에서 번갈아** 재면 방당 CPU와 합격 여부가 다른가. 즉 방 500개 불합격은 코드 때문인가, 측정 세션 때문인가.
- **조건(방 수는 두 가지, 각각 이전과 새 서버를 번갈아):** 이전 서버는 부하를 쟀던 커밋 `cb9d3c8`을 별도 폴더(`C:\dev\yong_old`)에 내보내 Release로 빌드한 것(속도 300, 충돌 없음, 재생 위치 고정, 채집/건설 없음). 새 서버는 현재 작업 폴더의 Release(속도 360, 충돌, 구역, 재생). **부하 생성기는 둘 다 현재 것을 쓴다**(서버만 다르다). 방 500개와 400개, 조건당 3회, 실행 순서는 이전, 새, 이전, 새 ... 로 번갈아 한다. 나머지 고정은 재측정과 같다(Release, `--log-level info --stats-interval 1`, 생성기 4스레드, 워밍업 5초, 측정 30초).
- **판정 규칙(미리 정한다):** 같은 방 수에서 서버 CPU 중앙값이 **새 서버가 이전 서버보다 3%포인트 이상 높으면** 코드 비용이 있다고 본다(같은 조건 3회의 편차가 이 세션에서 최대 약 6%포인트였으므로 보수적으로는 5로 읽는다). 차이가 그 안이면 "코드 때문에 늘었다는 증거가 없다"고 적는다. 합격 여부(방 500개)는 합격 기준 그대로 판정한다.
- **한계(미리):** 이전 서버는 `--bench-*` 옵션과 틱 단계 계측이 없다. 이전 서버의 이동 검증 상한(틱당 15 cm)과 현재 생성기의 상한(18 cm)은 상한이 느슨한 쪽(18)이라 정합성 검사가 통과한다.

## 송신 스레드 분리 (개선 후보 A) 구현과 측정 계획 (측정 전에 확정)

원인 분해에서 틱 시간의 약 98%가 전송(Deliver)이고 그 비용이 소켓 송신 시스템 호출(1회 약 14~17 µs)임을 확인했다([deliver-breakdown.md](../results/stage4/deliver-breakdown.md)). 그래서 **소켓 읽기/쓰기를 여러 입출력 스레드가 나눠 맡고, 게임 로직(틱, 방, 채팅)은 여전히 스레드 하나**에서 돌리도록 서버를 바꿨다.

### 구현 (서버 옵션 `--io-threads N`, 기본 0)

- **논리 구역 / 입출력 구역.** 디코더, 채팅 방, 게임 서비스, 세션 목록, `Close`는 논리 스레드(`Server`에 넘긴 `io_context`, 스레드 1개)에서만 실행된다. 소켓, 읽기 버퍼, 송신 큐, 송신 큐 한도 검사는 **연결별 strand**에서만 만진다. 두 구역은 `dispatch`로만 넘나든다(`Session` 머리말 참고).
- **송신:** 논리 스레드가 메시지를 한 번 직렬화해 프레임을 만들고, 송신 큐에 넣고 `async_write`를 거는 일을 연결의 strand로 넘긴다. 송신 시스템 호출은 입출력 스레드가 한다.
- **수신:** 읽기는 연결마다 하나만 건다. 읽은 바이트는 논리 스레드가 처리하고, **처리를 마친 뒤에** 다음 읽기를 건다(읽기 버퍼를 복사하지 않아도 안전하고, 처리가 느린 연결이 TCP 흐름 제어로 늦춰지는 예전 동작이 유지된다).
- **닫기:** 입출력 구역에서 생긴 닫힘(읽기/쓰기 오류, 송신 큐 초과)은 논리 스레드에서 `Close`를 실행하게 넘기고, `Close`가 소켓 닫기를 다시 strand로 넘긴다.
- **`--io-threads 0`:** 입출력 풀을 따로 만들지 않고 논리 `io_context`가 입출력도 한다. 이때 `dispatch`는 그 자리에서 바로 실행되므로 예전 단일 스레드 동작과 같은 순서다(strand와 원자 변수의 비용만 더해진다).
- 세션은 입출력 풀을 공유 소유한다(소켓이 자신이 속한 `io_context`보다 먼저 소멸해야 한다). 서버 종료는 열린 소켓 닫기를 모두 입출력 스레드에 넘긴 뒤 풀을 비운다.

### 정확성 확인

- 기존 통합 테스트 3종(`server_integration_test`, `chat_integration_test`, `game_integration_test`)을 입출력 스레드 4개 서버로 한 번 더 돌린다(ctest 항목 `*_io4`, 환경변수 `GAME_TEST_IO_THREADS`). 전체 `ctest` 427개 통과(MySQL 11개 건너뜀), `*_io4`와 새 시험은 8회 반복해 모두 통과.
- 새 시험(`ServerIntegrationIoThreads`): 연결 24개가 동시에 파이프라인으로 보낸 150개 요청의 응답 순서(큰 응답 포함, 부분 쓰기), 큰 응답을 쓰는 중 상대가 연결을 끊는 상황 반복, 느린 수신자의 송신 큐 초과가 정상 연결에 영향이 없음, 트래픽이 한창일 때 서버 종료.
- 변형 검증: (M1) 종료 시 소켓을 닫지 않음, (M2) 송신 큐 초과를 닫지 않음, (M3) 논리 구역이 읽기 버퍼를 다 쓰기 전에 다음 읽기를 거는 경합. 세 가지 모두 시험이 잡았다.
- **구현 중 찾은 결함:** 서버가 먼저 소멸하고 논리 `io_context`의 대기 핸들러가 나중에 세션을 해제하면, 그 세션의 소켓이 이미 사라진 입출력 풀을 건드려 프로세스가 가끔 죽었다(`*_io4` 채팅 시험이 가끔 비정상 종료해서 발견). 세션이 풀을 공유 소유하도록 고쳤고, 그 시험을 60회 반복해 0회 실패했다.

### 측정 계획

- **질문:** 같은 게임 코드에서 소켓 입출력 스레드를 늘리면 방 몇 개까지 합격하는가. 틱 스레드의 전송 시간(Deliver)은 얼마나 줄어드는가.
- **한 번에 한 변수 = 입출력 구조.** 서버 게임 코드는 같고 입출력만 다르다. 조건:
  - `PRE`: 입출력 분리 이전 서버. 같은 작업 폴더에서 `session.*`, `server.*`만 커밋 `03722ec` 버전으로 되돌린 빌드(`C:\dev\yong_pre`, 게임 코드와 측정용 `--bench-*` 옵션과 틱 단계 계측은 같다).
  - `IO0`: 새 코드, `--io-threads 0` (분리 구조의 오버헤드만 있고 스레드는 하나. `PRE`와 비교해 분리 구조 자체의 비용을 본다)
  - `IO1`, `IO2`, `IO4`: 새 코드, `--io-threads 1 / 2 / 4`
- **방 수와 반복:** 방 500, 600, 400개(이 순서). 조건당 3회, 매 실행 새 서버 프로세스. 실행 순서는 방 수마다 `PRE, IO0, IO1, IO2, IO4`를 한 바퀴로 하여 3바퀴(같은 세션에서 번갈아). 400개는 CPU가 포화되지 않는 지점의 효율 비교용이다.
- **추가 규칙(결과를 보기 전에 정한다):** 어떤 조건이든 600개가 3회 모두 합격하면 그 조건에 한해 700개를 더 잰다(조건당 3회). 500개에서 `PRE`가 3회 모두 합격이면 합격 여부로는 개선을 가르지 못하므로 CPU와 틱 시간으로만 판단한다.
- **고정:** Release(MSVC 14.44), 서버 `--log-level info --stats-interval 1`, 생성기 `--threads 4`, 방당 4명, 입력 초당 10번, 워밍업 5초, 측정 30초, 반영 대기 3초, 같은 PC 루프백. 합격 기준은 위 표 그대로다(바꾸지 않는다). 실행 도구는 `results/stage4/run-load-io.ps1`.
- **측정 오염 방지(이전 비교가 PC의 다른 프로그램 때문에 무효가 된 경험에서):** 실행 전에 사용자가 게임과 배경 프로그램을 닫는다. 도구는 매 실행 직전에 PC 전체 CPU 사용률을 5초 재서 10%를 넘으면 안정될 때까지(최대 2분) 기다리고, 그래도 넘으면 그 실행을 `contaminated`로 표시해 집계에서 뺀다(숨기지 않고 따로 기록한다). 실행 중의 PC 전체 CPU도 같이 기록한다.
- **판정 규칙:**
  1. **주 판정:** 조건별 최대 안정 방 수(3회 모두 합격한 가장 큰 방 수). 어떤 `IOn`의 값이 `PRE`보다 크면 "방 수가 늘었다".
  2. **보조 판정(방 400개):** 서버 통계 줄의 틱 단계 시간 중 **전송(Deliver) ms/s의 중앙값**이 `PRE`보다 30% 이상 줄면 "틱 스레드의 전송 부담이 줄었다". 서버 프로세스 전체 CPU(여러 스레드 합, 코어 하나가 100%)는 더 늘 수 있으므로 **비용이 아니라 병렬화의 대가로** 함께 적는다.
  3. `IO0`가 `PRE`보다 방 400개의 서버 CPU 중앙값이 3%포인트 이상 높거나 합격 방 수가 낮으면 "분리 구조 자체에 비용이 있다"고 적는다.
  4. 개선이 없으면 없다고 적는다(스레드 수를 늘려도 이득이 없거나 오히려 나빠질 수 있다).
- **미리 적어 두는 한계:** 부하 생성기(4스레드)와 서버가 같은 PC의 코어를 나눠 쓴다. 입출력 스레드를 늘려도 생성기와 코어 경쟁이 있어 이득이 작게 나올 수 있고, 이 PC에서의 결과가 서버 전용 기계의 결과가 아니다. 루프백 TCP는 송신 시스템 호출 안에서 수신 쪽 처리까지 일부 하므로 실제 네트워크와 비용이 다르다. Windows, Release, 이 PC 한 대의 결과다. Linux 결과는 없다.

### 측정 결과 요약

[results/stage4/io-threads.md](../results/stage4/io-threads.md)에 표와 해석, 한계가 있다. 요약(같은 세션에서 번갈아, 조건당 3회):

- **방 수가 늘었다.** 분리 이전(`PRE`)은 500개에서 3회 모두 불합격(누락 4.8~7.8%)이었고, 입출력 스레드 2개(`IO2`)는 600개까지, 4개(`IO4`)는 **700개까지 3회 모두 합격**했다(`IO4`의 상한은 찾지 못함, 사전 규칙이 700개까지였다).
- **틱 스레드의 전송 시간이 92% 줄었다**(방 400개, 759에서 약 57 ms/s). 병목이 틱 스레드에서 입출력 스레드로 옮겨 갔다. 대가로 서버 프로세스 전체 CPU가 약 25% 늘었다(85%에서 105%).
- **`--io-threads 0`(분리 구조, 스레드 하나)은 이전보다 느렸다**(방 500개 누락 14.7% 대 6.7%). 분리 구조 자체에 비용이 있다.
- **`--io-threads 1`은 쓰면 안 된다.** 누락 스냅샷은 0인데 입력 반영 지연이 6~11초로 쌓인다(입출력 스레드 하나가 포화되어 읽기가 밀림). 도착 간격만 보면 놓치고 입력 반영 지연 기준이 잡았다.
- 방 400개의 `IO0`/`IO1` 실패와 방 700개 `IO2`의 2회 불합격은 PC 부하(다른 프로그램)가 섞였을 수 있다. 방 500/600개 결과는 PC가 안정된 구간이라 3회가 같은 방향이다.
- 기본값은 `--io-threads 0` 그대로다. 기본값을 바꾸려면 스레드 수와 느린 연결의 스냅샷 대체(밀린 송신 큐에 낡은 스냅샷을 쌓지 않기)를 먼저 정해야 한다.

## 겪은 문제 (구현 중 발견)

| 문제 | 원인 | 수정 |
| --- | --- | --- |
| 방향 값이 매우 큰 입력(예: 1e30)에서 이동이 멈추거나 위치가 NaN이 될 수 있었다 (단위 테스트가 발견) | 방향 길이를 `float`로 제곱해 구하다 1e30 이상에서 무한대로 넘침. 무한대로 나누면 0이 되고, 두 성분이 모두 크면 무한대/무한대로 NaN이 되어 위치가 망가진다 | 길이를 `double` `hypot`으로 구한다. 회귀 시험(`FLT_MAX` 포함 5가지)을 추가 |
| 타이머 시험에서 스냅샷 수가 틱 수보다 적게 나옴 | 윈도우 기본 타이머 해상도(약 15.6 ms) 때문에 틱이 늦게 깨어나 몰아서 처리(따라잡기)하므로 한 번에 여러 틱을 계산하고 스냅샷은 한 번만 보낸다. 서버가 의도한 동작이다 | 시험이 "스냅샷 수 <= 처리한 틱 수"와 "마지막 스냅샷의 틱 번호 = 처리한 틱 수"를 확인하도록 고침. 서버 `main`은 3단계에서 쓴 타이머 해상도 올리기를 적용 |
| 부하 측정 집계에서 틱 건너뜀이 합격 기준을 넘는 것처럼 나옴 | 집계가 측정 종료 **이후** 첫 서버 통계 줄까지 포함해, 생성기가 연결을 한꺼번에 닫는 정리 구간이 섞임. 클라이언트가 본 최대 간격(62~85 ms)과 맞지 않아 발견 | 측정 종료 이전 마지막 줄까지로 구간을 고침(정리 구간 값은 따로 기록). 합격 기준은 그대로 |
| 시험 도우미가 방에 들어가 있는 연결에서 실패 | 방에 있으면 응답 사이에 스냅샷, 방 알림, 채팅 전파가 끼어들어 "예상하지 못한 ID"로 판정됨 | 게임용 도우미(`kGameSkip`)가 끼어드는 종류를 건너뛰도록 함 (서버가 아니라 시험 도우미의 문제) |

## 알려진 제한

- (이 단계를 끝낸 시점의 제한이었고 이후 해소됨) Unreal 클라이언트와 아직 연동하지 않았다. 이후 Unreal 5.8 클라이언트가 이 프로토콜로 접속해 이동, 채집, 건설까지 시험을 통과했다([unreal-client.md](unreal-client.md)).
- **부하 측정은 같은 PC의 루프백, Windows, Release 한 대의 결과다.** 방 25~700개(플레이어 100~2,800명)를 재서 최대 안정 규모를 방 500개로 기록했다([결과 기록](../results/stage4/game-load.md)). 실제 네트워크, 다른 입력 빈도, 채팅 등 다른 메시지가 섞인 부하는 재지 않았다.
- 스냅샷을 받는 사람마다 같은 메시지를 따로 직렬화한다(방 4명이면 4번). 병목이라는 증거가 없어 최적화하지 않았다.
- 이동 입력은 초당 횟수 제한이 없다. 입력 하나는 가벼워 서버가 감당하지만(방 20개 시험 통과), 악의적인 클라이언트가 초당 수만 번 보내는 경우는 막지 않는다.
- 플레이어끼리 충돌, 장애물, 월드 저장은 범위 밖이다(장애물은 이후 조각 1의 이동 충돌로, 저장은 [persistence.md](persistence.md)로 들어왔다. 플레이어끼리 충돌은 여전히 없다). 방 안 채팅도 없고 기존 채팅은 전체 방 하나다.
- 송신 큐가 가득 찬 느린 수신자가 스냅샷 때문에 끊기는 경우는 단위 테스트(전송 중 연결 종료)로만 확인했고, 실제 TCP로 만드는 시험은 하지 않았다(소켓 버퍼가 커서 시간이 오래 걸림). 같은 메커니즘(`Session` 송신 큐 한도)은 채팅 통합 테스트에서 확인했다.
