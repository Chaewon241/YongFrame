# 4단계 확장 1: 자원 채집

> 상태: **서버와 Unreal C++ 구현 완료(Windows). 에디터 쪽 에셋(MCP)과 PIE 확인은 남음.** 설계와 합격 기준은 구현 전에 쓴 것이고, 구현 뒤의 검증 결과는 아래 "검증 결과"에 있다. 값은 사용자가 정하지 않아 **임의 기본값**이고 `PlayConfig`에서 바꾼다. 최소 구현([stage4.md](stage4.md))은 건드리지 않고 메시지와 필드를 더하는 방식으로만 확장했다.

## 목표

[game-plan.md](game-plan.md)의 확장 5번(나무, 돌을 쳐서 자원 획득)의 **가장 작은 한 바퀴**를 만든다. 서버가 월드 상태(자원 노드의 체력과 재생)와 판정(거리, 쿨다운)을 소유하고, 클라이언트는 "이 노드를 채집하고 싶다"는 요청만 보낸다. 이 한 바퀴가 돌면 집 짓기, 농사 같은 이후 확장도 같은 모양(서버 상태 + 방 전체 알림 + 요청/응답)으로 붙일 수 있다.

## 범위

포함
- 나무(목재)와 돌(석재) 자원 노드. 맵에 고정 배치, 서버가 소유
- `E` 키로 가까운 노드를 쳐서 자원 획득, 노드 체력 감소와 고갈, 일정 시간 뒤 재생
- 플레이어별 인벤토리(목재, 석재 개수), HUD 표시
- 늦게 입장한 사람도 현재 노드 상태를 받는다

제외 (필요해지면 다음 확장에서)
- 도구(도끼, 곡괭이)와 도구별 효율, 아이템 종류 확장, 인벤토리 칸 제한
- 노드가 이동을 막는 충돌(플레이어는 노드를 통과한다)
- 인벤토리와 노드 상태의 DB 저장(방이 닫히면 사라짐), 거래, 플레이어 간 아이템 전달
- 채집 애니메이션/효과음(블루프린트 이벤트 자리만 둔다)
- 클라이언트 예측(채집 결과는 서버 응답을 받은 뒤 반영)

## 프로토콜 (`proto/game.proto`에 추가, ID는 `src/protocol/message_ids.h`)

기존 메시지는 바꾸지 않는다. 더하는 것은 모두 하위 호환이다(필드 추가, 새 ID, 새 열거값).

| ID | 메시지 | 방향 | 설명 |
| ---: | --- | --- | --- |
| 107 | `GatherRequest{node_id}` | C→S | 그 노드를 한 번 친다 |
| 108 | `GatherResponse{result, node_id, wood, stone}` | S→C | 결과 코드와 **내** 인벤토리 합계(성공/실패 모두 현재 값) |
| 112 | `ResourceUpdate{tick, nodes[{node_id, hp}]}` | S→C | 틱 끝에 **바뀐 노드만** 모아 방 전원에게(채집한 본인 포함). `hp == 0`이면 고갈 |

추가 필드: `RoomState.nodes = 5`(`repeated ResourceNode{node_id, kind, x, y, hp, max_hp}`). 방 만들기/입장 응답에 현재 모든 노드가 담긴다. `kind`는 `RESOURCE_TREE = 0`, `RESOURCE_ROCK = 1`이다. `node_id`는 방 안에서 1부터 부여하고 방이 닫힐 때까지 같다.

추가 결과 코드(`GameResult`): `GAME_NODE_NOT_FOUND = 9`, `GAME_NODE_DEPLETED = 10`, `GAME_TOO_FAR = 11`, `GAME_GATHER_COOLDOWN = 12`. 방에 없는 연결은 기존 `GAME_NOT_IN_ROOM`.

판정 순서(위에서부터 처음 걸리는 것): 방에 없음 → 노드 없음 → 고갈 → 너무 멂 → 쿨다운. 거부된 요청은 **상태를 바꾸지 않고**(체력, 인벤토리, 쿨다운 기준 틱 모두 그대로) 응답만 한다. 연결은 유지한다.

규칙
- 채집은 요청이 도착한 시점의 서버 위치로 판정하고 즉시 반영한다. `ResourceUpdate`는 바로 뒤 틱 끝에 간다(최대 50 ms 뒤). 한 틱에 같은 노드가 여러 번 바뀌어도 업데이트는 한 번(마지막 값)이다. 따라잡기 틱으로 틱이 합쳐져도 바뀐 노드는 누락되지 않는다.
- 같은 틱에 여러 명이 같은 노드의 마지막 체력을 두고 요청하면 도착 순서대로 처리하고, 체력은 0 아래로 내려가지 않는다. 마지막 한 번을 친 사람만 성공하고 나머지는 `GAME_NODE_DEPLETED`다.
- 재생은 고갈된 틱부터 600틱 뒤다. 재생된 노드는 `ResourceUpdate`로 알린다.
- 인벤토리는 플레이어가 방을 나가면 사라진다(저장 없음). 입장한 사람은 0에서 시작한다.
- 응답 수는 요청 수와 같다(Ping과 같은 1:1). 요청을 쿨다운 없이 마구 보내도 상태는 바뀌지 않는다.

## 완료 기준 (구현 전에 확정)

서버
1. **채집 성공:** 범위 안의 살아 있는 노드를 치면 `GAME_OK`, 노드 체력 1 감소, 내 인벤토리 1 증가(나무는 목재, 돌은 석재), 응답의 합계가 맞고, 틱 끝에 방 전원이 `ResourceUpdate`를 받는다.
2. **거부 5종:** 방에 없음, 없는 `node_id`, 고갈된 노드, 허용 거리 밖, 쿨다운 중이 각각 정해진 코드를 돌려주고 상태가 바뀌지 않는다. 허용 거리는 경계(200.0 허용, 200.01 거부)를 시험한다. 판정 순서(예: 멀고 쿨다운 중이면 `GAME_TOO_FAR`)도 시험한다.
3. **고갈과 재생:** 체력 0이면 고갈이고 그 뒤 채집은 거부된다. 고갈 틱에서 **정확히 600틱 뒤** 체력이 가득 차 돌아오고 알림이 가며(599틱 때는 아직), 재생 전에는 채집할 수 없다.
4. **쿨다운:** 같은 플레이어의 연속 채집은 10틱 간격(경계 포함)이어야 받아들여지고, 다른 플레이어는 서로 영향이 없다.
5. **경쟁:** 한 틱에 4명이 마지막 체력 노드를 치면 정확히 한 명만 성공하고 체력은 음수가 되지 않는다.
6. **격리:** 다른 방의 같은 `node_id`를 건드리지 않는다. 인벤토리는 플레이어별이다. `ResourceUpdate`는 같은 방 사람에게만 간다.
7. **늦은 입장:** 일부 체력이 깎인 노드와 고갈된 노드가 입장 응답의 `RoomState.nodes`에 현재 값으로 담긴다.
8. **배치:** 같은 설정이면 같은 배치(결정적), 노드 수가 설정과 같고, 모두 맵 안, 최소 간격 유지, 시작 영역이 비어 있다.
9. **견고함:** 나간 직후의 요청, 연결이 끊기는 도중의 요청, 아주 큰 `node_id`에서 서버가 죽지 않는다. 노드가 없는 방(설정으로 0개)도 동작한다.
10. **기존 기능 유지:** 기존 `ctest` 218개가 그대로 통과한다. 새 테스트는 **변형 검증**(고의로 버그를 심어 잡히는지 확인: 거리 비교 `<=`를 `<`로, 쿨다운 검사 제거, 재생 틱 하나 어긋나게, 체력 음수 허용, 방 사이 상태 공유 등)을 한다.
11. **문서:** 이 문서, [stage4.md](stage4.md) 프로토콜 표, [unreal-client.md](unreal-client.md)에 기준 바이트를 남긴다.

부하(선택): 기존 게임 부하 측정(방 500개, 4명, 입력 10/s)을 같은 합격 기준으로 한 번 다시 잰다. 입장 응답이 커지고 틱 경로에 "바뀐 노드 확인"이 추가되므로, 바뀐 노드가 없는 틱의 추가 비용이 눈에 띄면 안 된다. 합격 기준은 [stage4.md](stage4.md)의 게임 부하 기준을 그대로 쓴다. 채집 요청이 섞인 워크로드는 이번에 재지 않는다(재지 않았으니 수치를 주장하지 않는다).

Unreal
12. **자동 시험(`GameClientSpike`):** 진짜 서버에 채집 요청을 보내 성공, 거부(너무 멂, 쿨다운), `RoomState.nodes` 파싱, `ResourceUpdate` 반영, 늦은 입장자가 현재 상태를 받는 것을 확인한다. 위젯 문구 도우미 시험(결과 코드별 한국어 문구가 서로 다름)을 확장한다.
13. **PIE(사람이 확인):** 창 2개에서 한쪽이 나무를 치면 다른 쪽 화면에서도 같은 나무가 깎이고 사라지며 30초 뒤 돌아온다. 인벤토리는 친 사람 HUD에만 오른다.

## 서버 설계

- `src/play/resources.h/.cpp`(`play_core`): 노드 배치 생성(고정 시드의 자체 난수 생성기. 표준 라이브러리의 분포는 구현마다 값이 달라 쓰지 않는다), 노드 상태, "이 위치에서 이 노드를 틱 T에 칠 수 있는가"의 순수 계산, 재생 대기열. 소켓과 시간을 모른다(틱 번호를 인자로 받는다).
- `Room`이 노드 집합과 플레이어별 인벤토리, 마지막 채집 틱을 가진다. `GameService`가 요청을 받아 `Room`에 넘기고, 틱에서 재생을 진행하고 바뀐 노드를 모아 `ResourceUpdate`를 방 전원에게 보낸다(기존의 "계산 → 수신자 확보 → 전송" 순서 유지).
- `Session`은 107을 파싱해 `GameService`에 위임한다. 알 수 없는 ID나 파싱 실패는 기존처럼 연결을 닫는다.
- 통계: 채집 성공 수, 거부 수(이유별), 고갈/재생 수를 기존 `Stats`에 더한다.
- `game_client`에 `/gather <node_id>`와 `/nodes`(현재 노드 목록 출력)를 더해 터미널로 같은 흐름을 먼저 확인한다.

## Unreal 설계

- `FGameClient`: `Gather(node_id)`와 108/112 처리, 방 상태의 노드 목록 보관. `UYongNetSubsystem`: `Gather`, `GetResourceNodes`, `GetInventory`, 이벤트(`OnGatherResult`, `OnResourcesChanged`).
- `AYongResourceNodeActor`(C++): 노드 번호, 종류, 체력을 받아 표시한다. 메시 후보 배열(`MeshVariants`, 노드 번호로 고른다)과 `Hit`/`Depleted`/`Respawned` 블루프린트 이벤트가 있다. 기본 동작이 블루프린트 그래프 없이도 되도록 C++가 처리한다: 고갈되면 숨김, 맞으면 짧게 눌리는 연출, 목표로 고르면 약간 커짐. 충돌은 없다.
- `AYongRoomGameMode`: `TreeNodeClass`, `RockNodeClass`로 서버 노드 목록에서 액터를 만들고(방 입장 후 첫 틱), 알림에 따라 갱신하고, 레벨을 떠날 때 지운다.
- `AYongPlayerController`: `E`를 누르고 있으면 내 화면 위치에서 150 cm 안의 살아 있는 노드 중 가장 가까운 것을 골라 0.5초마다 `Gather`를 보낸다(클라이언트 쿨다운은 서버와 같지만 판정은 서버가 한다). 거리 밖이면 보내지 않는다.
- `UYongHudWidget`: 새 위젯 이름은 **`BindWidgetOptional`**(`WoodText`, `StoneText`, `HintText`)로 둬서, 블루프린트에 아직 없어도 컴파일이 깨지지 않게 한다(필수 이름을 늘리면 `WBP_HUD`가 MCP 작업 전까지 컴파일 실패).
- 서버 결과 코드가 늘어나므로 `EYongGameResult`와 문구(`YongUi::DescribeResult`)도 늘린다. 문구 시험의 "모두 서로 다름" 검사가 누락을 잡는다.

### MCP 작업 목록 (S2, 에디터 작업만. 로직은 C++가 한다)

이 작업은 S1이 끝나 C++ 클래스가 존재해야 시작할 수 있다(S0, S1은 끝났다).
1. **L_Farm 정리:** 손으로 배치한 나무와 돌(`SM_Tree*`, `SM_Rock*`, `SM_StoneTallA`) 인스턴스를 지운다. 이제 서버가 위치를 정하므로 남기면 "채집되지 않는 나무"가 생긴다. 풀과 꽃(`SM_GrassLarge`, `SM_FlowerRedA`)은 장식으로 둔다.
2. **`BP_ResourceTree`, `BP_ResourceRock`:** 부모 `AYongResourceNodeActor`. `MeshVariants`에 나무는 `SM_TreeDefault`, `SM_TreeFat`, `SM_TreeOak`, 돌은 `SM_RockLargeA`, `SM_RockSmallA`, `SM_StoneTallA`를 넣는다. 충돌은 끄고(`NoCollision`), 메시 크기를 cm 기준으로 맞춘다(나무 높이 약 300 cm, 큰 돌 약 100 cm. 현재 크기를 확인하고 보정 배율을 정해 보고).
3. **`BP_YongRoomGameMode`:** `TreeNodeClass = BP_ResourceTree`, `RockNodeClass = BP_ResourceRock`.
4. **`WBP_HUD`:** 인벤토리 `WoodText`, `StoneText`(TextBlock, 기본 "목재: 0", "석재: 0")와 `HintText`(기본 "E: 채집")를 추가한다. 위치는 방 코드 패널 아래.
5. (선택, 나중) `Hit`/`Depleted`/`Respawned` 이벤트에 소리나 입자 연결. 이번 한 바퀴에는 넣지 않는다.

사용자가 직접 확인할 것: Kenney 메시의 라이선스(문서에 적어야 한다).

## 재생 위치 변경 (구현 뒤에 바뀐 것)

처음 설계는 "노드의 위치는 바뀌지 않고 체력만 바뀐다"였다. 집 짓기가 들어오면서 **재생할 때 노드가 새 자리에 나타나도록 바뀌었다**(구조물이 원래 자리를 차지했거나 사람이 서 있을 수 있기 때문이다).

- 재생 시각이 되면 서버가 맵 안에서 새 자리를 고른다. 같은 설정, 같은 노드, 같은 틱이면 같은 자리가 나오는 결정적 난수다(시험이 결정적이다). 처음 배치와 같은 규칙(가장자리 여백, 시작 영역 비움, 다른 노드와 최소 간격 150 cm)에 더해, **구조물 발자국(건설 중 포함)과 플레이어의 몸 위는 피한다**.
- 자리를 찾지 못하면 노드는 고갈 상태로 남고 **다음 틱에 다시 찾는다.**
- `ResourceUpdate`의 노드 항목에 `x`, `y`가 더해졌다(하위 호환). 클라이언트는 방 상태의 노드 위치를 갱신하고 액터를 옮긴다.
- **구역 분리로 보강했다**(아래와 [content-roadmap.md](content-roadmap.md)의 "구역 분리"): 노드는 맵 중앙의 건설 구역 밖에만 놓이고 재생하므로, 건물이 늘어도 노드가 설 자리가 줄지 않는다. 자리를 못 찾은 노드는 매 틱이 아니라 20틱(1초)마다 다시 찾는다(`respawn_retry_ticks`).
- 이 변경의 시험은 `play_resources_test`에 있다. 재시도 간격과 구역 규칙은 변형 검증을 했다(구역 절).

## 위험과 알려진 한계 (설계 시점)

- `RoomState`가 커진다(노드 50개, 대략 1 KB 안팎). 입장 때만 한 번 보내고 틱 경로에는 영향이 없어야 하며, 위 부하 확인으로 본다.
- 거리 판정은 서버 위치 기준이라 지연이 큰 클라이언트에서는 "가까워 보이는데 `GAME_TOO_FAR`"가 날 수 있다. 서버 허용 거리(200)를 클라이언트 선택 거리(150)보다 넓게 둔 이유다.
- 노드 충돌이 없어 플레이어가 나무 안에 들어간다. 의도된 제한이며 다음 확장에서 다룬다.
- 노드 상태는 저장하지 않는다. 방이 닫히면 사라진다.
