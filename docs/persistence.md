# 계정과 농장 저장 (MySQL 영속화) 설계

> 상태: **P1(계정: 가입, 로그인, 내 기록, 중복 접속 거부, 실패 횟수 제한)과 P2(농장 저장: 집, 인벤토리, 누적 기록)는 서버에 구현했고 시험했다(Windows, 인메모리 저장소 기준). 실제 MySQL 시험은 사용자가 실행해야 한다. P3(Unreal 로그인 화면)는 C++와 커맨들릿 시험, 에디터 에셋(위젯 추가)까지 끝났고 PIE 확인은 진행 중이다(그 과정에서 복원한 인벤토리가 클라이언트에 전달되지 않던 빈틈을 찾아 고쳤다. 아래 저장 규칙의 "복원한 인벤토리를 클라이언트에 알려 준다"). P4(저장 켬/끔 부하 측정)는 아직 안 했다.** 아래 "결정"은 사용자가 정했고, "기본값으로 정한 것"은 제가 임의로 정한 값이라 바꿀 수 있다. 합격 기준은 측정 전에 쓴 것이다. 이 문서는 프로젝트 `project.md`의 "단계별 제외 범위"(로그인, 암호화 제외)를 **로그인(ID/비밀번호)은 포함, TLS는 계속 제외**로 바꾸는 범위 변경도 함께 기록한다. P1의 구현 결과와 구현 중 정한 세부 사항은 이 문서 맨 아래 "P1 구현 결과"에 있다.

## 1. 목표

지금은 방이 닫히면 집과 인벤토리가 모두 사라진다. 계정으로 "나"를 식별하고, **내가 얼마나 채집했는지, 맵에 집이 몇 개인지**를 MySQL에 저장해 다시 접속하면 이어서 한다.

현재 구조의 사실(코드 기준):

- 서버는 플레이어가 누구인지 모른다. 닉네임은 방 안에서만 의미가 있고(`player_id`는 방이 닫힐 때까지만 유효), 인벤토리(목재/석재)는 방 메모리에만 있다.
- 구조물은 방 안에서 1부터 번호가 붙고, 건설 진행은 방의 **틱 번호**(`ready_tick`)로만 안다.
- 자원 노드는 고정 시드로 배치되고 재생하며 상태를 저장하지 않는다.
- 이미 `ChatRepository`(비동기 인터페이스) + 인메모리/MySQL 구현, `db_migrate`, 번호 순서 마이그레이션이 있다. 같은 방식을 따른다.

## 2. 결정 (사용자)

| 항목 | 결정 |
| --- | --- |
| 저장 범위 | **농장(방)이 영속**한다(집의 위치와 상태). 각 플레이어의 인벤토리와 누적 기록은 계정에 저장한다 |
| 인증 | **ID + 비밀번호.** 서버는 솔트가 붙은 느린 해시만 저장한다. TLS는 이번 범위에 없다 |
| 저장 시점 | **혼합:** 건설은 즉시, 채집은 모아서 저장(몇 초마다, 방을 나갈 때, 서버 종료 때) |
| 게스트 | **유지.** 로그인 없이 닉네임만으로 하는 기존 방식은 저장 없이 그대로 둔다 |

## 3. 기본값으로 정한 것 (바꾸고 싶으면 알려 주세요)

| 항목 | 기본값 | 이유 |
| --- | --- | --- |
| 닉네임 | **로그인 ID가 곧 닉네임** | 가입 입력이 줄고, 기존 닉네임 규칙(16문자 이하)과 방 안 중복 검사를 그대로 쓴다 |
| ID 규칙 | 영문/숫자/밑줄 4~16자. 입력은 대소문자를 구분하지 않고 **소문자로 바꿔 저장**한다(`Alice_01`과 `alice_01`은 같은 ID) | 닉네임 규칙 안에 들어가고 혼동이 적다 |
| 비밀번호 규칙 | 8~64바이트(UTF-8) | 너무 짧은 것과 해시 비용을 키우는 긴 입력을 막는다 |
| 농장 수 | **계정당 1개.** 로그인한 사람이 방 만들기를 하면 자기 농장을 연다(없으면 만든다) | "내 농장"이 하나로 분명하고 방 코드가 고정된다 |
| 농장 입장 | 농장은 **주인이 열어 둔 동안에만** 코드로 입장할 수 있고, **로그인한 사람만** 들어온다. 닫혀 있으면 `ROOM_NOT_FOUND` | 주인 없이 농장을 불러오는 경로가 생기지 않는다 |
| 게스트 방 | 지금처럼 임시 방(저장 없음). 로그인한 사람이 게스트 방에 들어가는 경로는 없다 | 두 종류가 섞이지 않는다 |
| 중복 로그인 | 같은 계정이 이미 접속 중이면 **새 접속을 거부**한다 | 한 계정의 저장 값을 두 곳에서 동시에 바꾸는 경합을 없앤다 |
| 건설 중인 집 | 남은 틱 수(`remaining_ticks`)를 저장하고, 농장을 열 때 이어서 진행한다. **농장이 닫혀 있는 동안 시간은 흐르지 않는다** | 틱이 방 메모리 안의 시간이라서 |
| 자원 노드 | 저장하지 않는다(고정 시드로 다시 만들고 체력은 가득) | 상태가 없는 것과 같아서 저장 이득이 작다 |
| 인벤토리 | **(농장, 계정)별.** 누적 채집량/지은 집 수는 **계정별** | 인벤토리는 방에서 쓰는 자원이고 누적은 계정의 기록이다 |
| 저장 주기 | 채집 변경분은 10초마다 | 값은 측정 뒤 정한다 |
| 로그아웃 | 접속을 끊는 것이 로그아웃이다(전용 메시지 없음) | 최소 범위 |
| 범위 밖 | 비밀번호 변경/분실, 계정 삭제, 이메일, 여러 서버, TLS | 필요해지면 다음 조각 |

## 4. 구조

```
Session ── 로그인 상태(계정 번호, 닉네임)를 연결에 붙임
   │
   ├─ AccountService ── AccountRepository (인메모리 / MySQL)  가입, 로그인 확인
   │        └─ 비밀번호 해시 계산은 별도 일꾼 스레드 (로직/입출력 스레드를 막지 않음)
   │
   └─ GameService ── FarmRepository (인메모리 / MySQL)         농장 불러오기, 저장
            ├─ 로그인한 연결의 방 만들기: 농장 불러오기(비동기) → 농장 방 생성
            └─ 저장 규칙(5절): 건설 즉시, 채집은 모아서, 나갈 때, 종료 때
```

- 저장소 인터페이스는 `ChatRepository`와 **같은 규칙**을 따른다: 결과는 핸들러로, 핸들러는 항상 반환 뒤 로직 스레드에서, 정확히 한 번. 그래서 DB가 느려도 게임 틱을 막지 않고 잠금이 필요 없다. 시험용 인메모리 구현은 실패와 지연을 주입할 수 있다.
- MySQL 구현은 `MysqlChatRepository`처럼 연결 1개 + 작업 큐 직렬화, 모든 호출에 제한 시간, 오류 시 연결 폐기 후 재연결, 준비된 문장 바인딩이다.
- **서버의 게임 규칙(`Room`, `World`)은 DB를 모른다.** 저장 모양의 상태를 받아 방을 복원하는 함수와 저장할 상태를 내놓는 함수만 더한다.

### 비밀번호 해시 (가장 조심할 곳)

- **라이브러리:** libsodium의 `crypto_pwhash_str`(Argon2id, 솔트와 비용 매개변수가 결과 문자열에 들어 있음). 직접 만들지 않는다. vcpkg에 `libsodium` 포트가 있고 `vcpkg.json`에 의존성을 추가해야 한다(baseline은 그대로, 첫 구성에서 소스 빌드).
- **해시는 비싸다**(메모리를 쓰고 수십 ms). 로직 스레드나 입출력 스레드에서 돌리면 틱이 밀린다. **일꾼 스레드 풀(작은 크기, 기본 2)** 에서 계산하고 결과만 `dispatch`로 로직 스레드에 돌려준다. 대기 중인 해시 작업 수에 상한을 둔다(넘으면 `STORAGE_BUSY`로 거부).
- **무차별 대입 방지:** 한 연결에서 로그인 실패 5회면 그 연결을 닫는다. 오류 응답은 "ID 또는 비밀번호가 틀림"으로 통일해 ID 존재 여부를 알려 주지 않는다(가입 때의 "ID 사용 중"은 불가피).
- 비밀번호는 로그와 오류 메시지에 남기지 않는다. 서버는 해시를 클라이언트에 보내지 않는다.
- **TLS가 없어 비밀번호가 네트워크에 평문으로 흐른다.** 로컬 개발 환경에서는 영향이 없지만 이 한계를 문서(README, 이 문서)에 명시한다. TLS는 다음 조각이다.

## 5. 저장 규칙

모든 저장은 **절대값 upsert**로 한다(증가분이 아니라 "지금의 값"을 쓴다). 그래서 실패하면 다음 번에 같은 값을 다시 써도 되고(멱등), 같은 값을 두 번 써도 문제가 없다.

| 사건 | 저장 |
| --- | --- |
| 건설 성공 | 즉시: 구조물 행, 건설자의 인벤토리(자원 차감), 계정의 `houses_built`를 한 트랜잭션으로 |
| 건설 완공 | 즉시: 그 구조물 상태 갱신 |
| 채집 성공 | 메모리의 (농장, 계정) 인벤토리와 계정 누적에 `dirty` 표시만 하고, **10초마다** 모인 것을 한 번에 저장 |
| 방 나가기, 농장 닫힘 | 그 사람의 `dirty`를 바로 저장. 농장이 닫힐 때 건설 중인 집의 남은 틱 저장 |
| 서버 종료 | 모든 `dirty`와 열린 농장을 저장하고 제한 시간(기본 5초) 안에 끝나지 않으면 포기하고 로그를 남긴다 |
| DB 장애 | **게임은 계속 진행한다.** 저장은 `dirty`로 남아 다음 주기에 다시 시도한다. 연속 실패 수와 마지막 오류를 통계에 노출하고, 서버가 비정상 종료하면 마지막 저장 이후의 변경은 잃는다(한계) |

서버가 갑자기 죽을 때의 손실 한도는 "마지막 성공 저장 이후의 채집량"이다. 건설은 즉시 저장하므로 집은 잃지 않는다(저장이 실패한 상태가 아니었다면).

## 6. 스키마 (마이그레이션 `002`~, 번호 순서, 적용한 파일은 고치지 않음)

문자 집합은 `utf8mb4`, 시각은 `*_unix_ms`(기존 방식).

| 테이블 | 열 | 비고 |
| --- | --- | --- |
| `accounts` | `id` PK(AI), `login_name` VARCHAR(16) **UNIQUE**(대소문자 구분 없음), `password_hash` VARCHAR(255), `created_at_unix_ms` | 평문 비밀번호는 어디에도 없다 |
| `account_stats` | `account_id` PK(FK), `wood_gathered`, `stone_gathered`, `houses_built`, `updated_at_unix_ms` | 누적 기록 |
| `farms` | `id` PK(AI), `code` CHAR(6) **UNIQUE**, `owner_account_id` **UNIQUE**(FK), `created_at_unix_ms` | 계정당 1개는 UNIQUE로 강제 |
| `farm_structures` | `farm_id`, `structure_id`, `type`, `x`, `y`, `state`, `remaining_ticks`, `built_by_account_id`, PK(`farm_id`, `structure_id`) | 방 안 번호를 그대로 쓴다. 불러올 때 다음 번호는 최댓값 + 1 |
| `farm_players` | `farm_id`, `account_id`, `wood`, `stone`, PK(`farm_id`, `account_id`) | 농장별 인벤토리 |

**농장 방 코드:** 지금 방 코드는 메모리에서만 겹치지 않으면 되었다. 농장 코드는 DB의 UNIQUE로 겹침을 막고(중복 키 오류면 다시 뽑는다), 게스트 방 코드는 **현재 열린 방과 겹치지 않고 DB의 농장 코드와도 겹치지 않아야** 한다(서버는 시작할 때 농장 코드 전체를 메모리에 올려 두고 농장 생성 때 갱신한다. 농장 수가 작은 동안의 단순한 방식이며 한계로 적는다).

## 7. 프로토콜 (메시지 ID는 `message_ids.h`가 기준, 번호는 제안)

| ID | 메시지 | 방향 |
| ---: | --- | --- |
| 120 / 121 | `RegisterRequest{login_name, password}` / `RegisterResponse{result}` | C→S / S→C |
| 122 / 123 | `LoginRequest{login_name, password}` / `LoginResponse{result, profile}` | C→S / S→C |
| 124 / 125 | `ProfileRequest{}` / `ProfileResponse{wood_gathered, stone_gathered, houses_built, farm_code, structures_in_farm}` | C→S / S→C |

- `result`(새 열거형 `AccountResult`): OK, 잘못된 ID 형식, 잘못된 비밀번호 형식, ID 사용 중, 자격 증명이 틀림, 이미 접속 중, 시도 횟수 초과, 저장소 사용 불가.
- 게임 결과 코드에 추가: `GAME_LOGIN_REQUIRED = 19`(농장 입장 등에 로그인이 필요), `GAME_STORAGE_UNAVAILABLE = 20`(농장을 불러오지 못함).
- 로그인한 연결의 `CreateRoomRequest`는 `nickname` 필드를 무시하고 계정의 닉네임(ID)을 쓴다. 기존 필드는 그대로라 게스트 흐름과 기존 클라이언트는 영향이 없다.
- 호환되지 않는 변경은 없다(메시지 추가만).

## 8. 검증 계획

- **단위:** ID/비밀번호 규칙, 해시 확인(맞는 것/틀린 것), 저장 상태 ↔ 방 복원의 왕복(구조물, 건설 중 남은 틱, 인벤토리).
- **인메모리 저장소 통합:** 가입 → 로그인 → 농장 만들기 → 채집/건설 → 나가기 → 다시 로그인 → **상태 복원**, 중복 로그인 거부, 틀린 비밀번호 5회에 연결 종료, 게스트는 농장에 입장 불가, 게스트 흐름은 기존 시험이 그대로 통과.
- **장애 주입:** 저장소가 실패/지연할 때 게임이 계속되고, 복구되면 `dirty`가 저장된다(멱등 확인). 서버 종료 중 저장 제한 시간.
- **실제 MySQL(`*_mysql_test`):** 사용자가 비밀번호를 환경변수로 주고 실행한다(채팅 때와 같은 규칙. **채팅 창에 비밀번호를 쓰지 않는다**). **서버 재시작 시험:** 서버를 완전히 내렸다 올린 뒤 같은 DB에서 농장이 복원된다.
- **변형 검증:** 이 저장소의 규칙대로 고의로 심은 버그를 시험이 잡는지 확인한다(예: 건설 즉시 저장 누락, `dirty` 미표시, 인벤토리 복원 누락, 남은 틱 복원 누락, 로그인 실패 횟수 미집계, 평문 비밀번호 로그 출력 등).
- Unreal: 커맨들릿 시험(로그인, 농장 복원)과 변형 검증, 에디터 확인은 사람이 한다. 에셋 작업(로그인 화면, 기록 표시)은 이 저장소의 MCP 작업 순서(S0 서버 → S1 Unreal C++ → S2 MCP → S3 사람)를 따른다.

## 9. 성능 영향 측정 계획 (측정 전에 확정)

저장은 서버를 느리게 할 수 있다. **기존 인메모리 측정은 바꾸지 않고**, 저장을 켠 구성을 따로 잰다.

1. **로그인 폭주:** 계정 N개(예: 200)가 동시에 로그인할 때 게임 틱이 밀리는가. 해시를 일꾼 스레드에 둔 설계가 맞는지의 확인이다. 판정: 이 동안 서버 틱 건너뜀이 0.1% 이하이고 다른 연결의 입력 반영 지연 p99가 100 ms 이하(4단계 기준 그대로). 조건(변수): 해시를 일꾼에서 계산 / 로직 스레드에서 계산(비교용 한 번만).
2. **저장 켬/끔 부하:** 부하 생성기에 로그인 모드를 더하고(계정은 미리 만들어 둠), 같은 방 수에서 **저장 끔(인메모리 저장소)** 과 **저장 켬(MySQL)** 을 같은 세션에서 번갈아 3회씩 잰다. 합격 기준은 4단계 부하 측정과 같다. 추가로 저장 대기열 길이, 저장 호출 지연 p99, 저장 실패 수를 기록한다. 한 번에 변수 하나(저장소 종류), 실행 전 PC 상태 확인과 번갈아 실행 규칙은 입출력 분리 측정과 같다.
3. 판정 기준의 구체 수치(방 수, 로그인 수)는 구현 뒤 첫 시험 실행을 하고 **측정 전에** 이 절에 적는다.

## 11. P1 구현 결과 (계정)

**구현한 것** (`src/account/`, `proto/account.proto`, `db/migrations/002_create_accounts.sql`)

| 구성 | 내용 |
| --- | --- |
| `account_rules` | ID(영문/숫자/밑줄 4~16자, 소문자로 정규화)와 비밀번호(8~64바이트) 규칙. 순수 함수 |
| `PasswordHasher` | 해시 인터페이스. 실제 구현 `SodiumPasswordHasher`(libsodium `crypto_pwhash_str`, Argon2id, 운영 비용은 메모리 64 MiB와 반복 2)와 시험용 빠른 가짜 |
| `AccountRepository` | 비동기 저장소 인터페이스(`CreateAccount`, `FindAccount`, `LoadStats`). 구현은 `InMemoryAccountRepository`(장애/지연 주입)와 `MySqlAccountRepository`(연결 1개 + 작업 큐, 제한 시간, 준비된 문장, 오류 시 연결 폐기. 테이블 이름 옵션은 시험이 운영 테이블을 건드리지 않게 하려는 것) |
| `AccountService` | 가입, 로그인, 내 기록, 연결별 로그인 상태, 중복 접속 거부, 실패 횟수 제한. 해시는 일꾼 스레드 풀(`--hash-workers`, 기본 2)에서 계산하고 결과만 로직 스레드로 돌려준다 |
| 연결 | `Session`이 새 요청(ID 120, 122, 124)을 `AccountService`로 넘기고, `GameService`가 로그인한 연결의 닉네임을 계정 ID로 바꾼다. `--storage mysql`이면 계정도 MySQL에 저장한다 |
| 도구 | `game_client`에 `/register <ID> <비밀번호>`, `/login <ID> <비밀번호>`, `/profile` |

**프로토콜 (확정):** 요청 `RegisterRequest`(120), `LoginRequest`(122), `ProfileRequest`(124)와 응답 121, 123, 125. 결과 코드 `AccountResult`는 `proto/account.proto`가 기준이다. 서버가 보내는 쪽 ID를 클라이언트가 보내면 알 수 없는 ID와 같이 연결을 닫는다.

**구현 중 정한 세부 사항**

- 로그인 실패 한도(기본 5회)를 넘으면 `ACCOUNT_TOO_MANY_ATTEMPTS`를 응답한 뒤 **200 ms 뒤에** 연결을 닫는다. 바로 닫으면 마지막 응답이 도착하기 전에 연결이 끊겨 클라이언트가 이유를 알 수 없기 때문이다. 그 사이의 로그인 시도는 해시를 계산하지 않고 거절한다.
- 형식이 틀린 로그인 입력은 해시를 계산하지 않고 바로 `ACCOUNT_BAD_CREDENTIALS`로 처리하되 실패 횟수에는 센다. **저장소 오류와 "이미 접속 중" 거부는 실패 횟수에 세지 않는다.**
- 없는 ID도 가짜 해시를 한 번 확인한다(서버 시작 때 만든 해시를 쓴다). 응답 시간으로 ID의 존재를 구분하기 어렵게 하려는 것이다. **이 효과는 측정하지 않았다.**
- 로그인 도중 누적 기록을 읽지 못하면 로그인을 되돌린다(0으로 보여 주면 나중에 저장할 때 기록을 덮어쓸 수 있으므로). 되돌린 계정은 "접속 중"으로 남지 않는다.
- 한 연결에서 인증 요청은 한 번에 하나만 처리한다. 이전 요청이 끝나기 전의 요청은 `ACCOUNT_SERVER_BUSY`다.
- P1의 "내 기록"은 저장소에서 읽은 누적값이다. 이 값을 채집/건설이 갱신하는 것은 P2다(P1에서는 항상 0이다).
- P1에서 **로그인한 연결도 방은 지금처럼 임시 방**이다(저장 없음). 로그인의 효과는 방에서 닉네임이 계정 ID로 고정되는 것뿐이다. 농장 영속과 "로그인한 사람만 농장 입장"은 P2다.

**검증 (Windows, Debug)**

- 단위: 입력 규칙 6개, 진짜 해시 6개(솔트, 비용 매개변수, 깨진 해시, NUL 포함 비밀번호), `AccountService` 23개(가입/로그인/중복 접속/실패 제한/저장소 장애/부분 실패 되돌리기/끊김/동시 가입/해시가 로직 스레드를 막지 않음/해시 대기열 상한).
- 통합(실제 TCP, `_io4` 변형 포함 각 17개): 가입, 로그인, 내 기록, 실패 5회 뒤 종료, 중복 접속, 접속 도중 이탈, 방에서의 닉네임, 게스트 흐름 유지, 저장소 장애와 지연이 다른 연결을 막지 않음, 비정상 입력, 24명 동시 가입과 로그인, 종료 중 로그인, **비밀번호가 가장 자세한 로그에도 남지 않음**, 진짜 Argon2id 한 번.
- 실제 MySQL 시험 `account_mysql_test` 15개 중 DB가 필요한 13개(저장소 9개, 서버 4개)는 비밀번호가 없는 환경에서는 건너뛰고, DB가 필요 없는 2개(위험한 테이블 이름 거부, 접속 불가 DB에 빨리 실패)는 항상 실행한다. **이 구현을 만든 환경에서는 실제 MySQL에 대해 실행하지 못했다**(비밀번호를 받지 않는 원칙). 사용자가 환경변수로 비밀번호를 주고 실행해야 한다(아래 "확인 방법").
- 변형 검증은 아래 결과 절.

**알려진 한계 (P1)**

- 비밀번호가 네트워크에 평문으로 흐른다(TLS 없음).
- 계정 삭제, 비밀번호 변경, 로그아웃 메시지는 없다(접속을 끊는 것이 로그아웃).
- 로그인 실패 제한은 **연결 단위**다. 같은 공격자가 연결을 새로 열면 횟수가 다시 시작한다(IP별 제한은 없다). 해시 대기열 상한(기본 64)이 서버 전체의 부담을 막는 마지막 방어선이다.
- 로그인 폭주 때 해시가 틱을 밀지 않는지는 **측정하지 않았다**(P4). 단위 시험은 해시가 로직 스레드 밖에서 돈다는 것만 확인한다.
- 계정 MySQL 저장소는 쓰기를 재시도하지 않는다(연결이 끊긴 순간의 가입은 사용자에게 `ACCOUNT_STORAGE_UNAVAILABLE`로 보인다).

## 12. P2 구현 결과 (농장 저장)

**구현한 것** (`src/farm/`, `src/play/farm_persistence.*`, `db/migrations/003_create_farms.sql`)

| 구성 | 내용 |
| --- | --- |
| `FarmRepository` | 비동기 저장소 인터페이스(`LoadFarmCodes`, `FindFarmByOwner`, `CreateFarm`, `SaveFarm`). **`SaveFarm` 한 번이 하나의 트랜잭션**(구조물, 인벤토리, 누적 기록의 절대값 upsert)이고, 같은 저장소의 요청은 호출한 순서대로 처리한다. 구현은 `InMemoryFarmRepository`(장애/저장만 장애/지연 주입)와 `MySqlFarmRepository`(연결 1개 + 작업 큐, 제한 시간, 준비된 문장, 오류 시 연결 폐기로 트랜잭션 취소) |
| `FarmPersistence` | **쓰기 대기열(write-back).** 게임 로직은 "이 값이 지금 이렇다"(절대값)만 알리고, 언제 쓸지는 여기서 정한다. 건설, 완공, 방을 나갈 때, 농장이 닫힐 때, 서버 종료 때는 **바로**, 채집은 `farm_flush_interval_ticks`(기본 200틱 = 10초)마다 **모아서** 저장한다. 실패하면 값이 대기열에 남아 다음 주기에 다시 저장한다(더 새로운 값이 있으면 그것이 이긴다). 농장 하나당 진행 중인 저장은 한 번에 하나다 |
| `GameService` | 로그인한 연결의 방 만들기 = **내 농장 열기**(없으면 만든다). 열 때 구조물과 인벤토리를 복원하고, 채집/건설은 계정의 누적 기록과 대기열에 알린다. 게스트 방은 그대로다. 농장 방에는 로그인한 사람만, 임시 방에는 로그인하지 않은 사람만 들어간다 |
| `AccountService` | 누적 기록을 로그인할 때 한 번 읽어 **메모리에 들고**, 채집/건설이 `AddProgress`로 더한다. "내 기록"은 이 메모리 값이라 저장 전에도 바로 보이고 저장소가 죽어도 응답한다 |

**프로토콜:** 게임 결과 코드에 `GAME_LOGIN_REQUIRED = 19`(게스트가 농장에 입장), `GAME_STORAGE_UNAVAILABLE = 20`(농장을 불러오거나 만들지 못함)을 더했다. 메시지 추가는 없다.

**구현 중 정한 세부 사항**

- **방 코드와 농장 코드:** 서버가 시작할 때 모든 농장 코드를 읽어 **예약**하고(`LoadFarmCodes`), 새 농장은 코드를 정하는 순간(저장소에 만들기 전) 예약해서 게스트 방이 같은 코드를 가져가지 못하게 한다. DB의 UNIQUE가 마지막 방어선이라 코드가 겹치면 다른 코드로 다시 만든다(최대 5번). 농장이 닫혀도 코드는 계속 예약된다.
- **이미 열린 농장:** 친구가 있는 동안 주인이 다시 접속해 방 만들기를 하면 **이미 열린 그 방에 들어간다**(농장을 두 번 열지 않는다).
- **여는 도중 연결이 끊기면** 방을 만들지 않는다(시험이 이 결함을 잡아 고쳤다: 처음에는 "여는 중" 표시를 지우지 않아 끊긴 연결을 위해 방이 만들어졌다).
- 농장을 여는 동안 같은 연결의 다른 방 만들기는 `GAME_SERVER_BUSY`다.
- 서버가 종료되면 열린 농장의 구조물, 방에 있는 사람들의 인벤토리와 누적 기록을 한 번에 저장한다(저장소 호출의 제한 시간 안에서 끝난다).
- 건설 중인 집은 남은 틱을 저장하고, **농장이 닫혀 있는 동안 시간은 흐르지 않는다**(다시 열면 남은 시간 뒤에 완공된다). 자원 노드는 저장하지 않는다.
- 같은 농장에서 방을 나갔다 들어온 사람의 인벤토리는 메모리(`FarmRuntime`)에서 되살린다. 저장이 아직 끝나지 않았어도 맞다.
- **복원한 인벤토리를 클라이언트에 알려 준다.** 처음에는 방 만들기/입장 응답에 인벤토리가 없어서 서버는 복원하는데 Unreal HUD는 0으로 보였다(다음 채집 응답이 와야 맞아졌다). P3의 PIE 확인에서 사람이 발견했다. 두 응답에 `wood`, `stone` 필드를 더해 해결했고(통합 시험 2개, 응답의 값을 하나씩 뺀 변형을 모두 잡음), Unreal은 응답에서 읽는다. **기존 시험은 서버의 값을 채집 응답으로만 확인해서 이 빈틈을 못 잡았다.**
- "내 기록"에 농장 코드와 집 수는 넣지 않았다. 지은 집 수(`houses_built`)는 누적이고 집을 허무는 기능이 없어 맵의 집 수와 같다.

**검증 (Windows, Debug, 인메모리 저장소)**

- 단위: `FarmPersistence` 11개(Flush 전에는 쓰지 않음, 한 번에 저장, 최신 값, 주기, 실패 뒤 복구, 오래된 값이 새 값을 덮지 않음, 농장당 진행 중 저장 하나, 종료 flush), `GameService` 농장 규칙 10개(코드 예약, 코드 충돌 재시도, 만드는 중 예약, 농장/임시 방 분리, 이중 요청, 종료 저장).
- 통합(실제 TCP, `_io4` 변형 포함 각 19개): 코드 유지, 계정마다 농장 8개 동시, 저장소 장애/지연, 연결 끊김, **재열기 뒤 인벤토리와 집과 누적 기록 복원**, 저장 시점(건설과 완공은 바로, 채집은 모아서, 짧은 주기는 방에 있는 채로 저장, 종료 때 저장), 저장 실패 뒤 재시도, 건설 중 닫혔다 열기(남은 시간과 시간 정지), 두 사람의 인벤토리 분리, 이미 열린 농장 재입장.
- 실제 MySQL(`account_mysql_test`의 농장 시험, 저장소 9개와 서버 2개): 코드/계정 중복 구분, 저장 왕복(float 좌표 포함), 같은 값 두 번 저장(멱등), **중간에 실패하면 전부 취소(롤백)**, 연결이 끊긴 뒤 같은 저장을 다시 보내면 성공, 20개 저장이 순서대로 적용, **서버를 완전히 껐다 켜도 농장(집, 인벤토리, 누적 기록)이 복원**, DB 장애 중의 저장이 재시도로 반영. **이 구현을 만든 환경에서는 실제 MySQL에 대해 실행하지 못했다**(비밀번호를 받지 않는 원칙). 사용자가 실행해야 한다.
- 변형 검증 22가지 중 21가지를 처음부터 잡았고, 살아남은 1가지("새 농장 코드를 만드는 도중 예약하지 않음")는 시험이 약했던 것으로 **저장소 응답을 기다리는 동안 게스트가 같은 코드를 가져가는 창을 확인하는 시험을 추가해 잡았다.**

**알려진 한계 (P2)**

- 서버가 비정상 종료하면 **마지막 저장 이후의 채집량**(최대 10초)을 잃는다. 건설과 완공, 방을 나갈 때는 바로 저장하므로 집은 잃지 않는다(저장이 성공했다면).
- 저장소가 오래 죽어 있으면 값이 메모리 대기열에 쌓인다(키별 최신 값 하나씩이라 크기는 농장 수 × 사람 수 × 집 수로 제한된다). 서버가 그동안 종료되면 잃는다.
- 농장 코드를 서버 시작 때 읽는다. 읽지 못하면(DB가 그때 죽어 있었다면) 게스트 방이 열리지 않은 농장의 코드를 쓸 수 있고, 그 농장은 열 때 `GAME_SERVER_BUSY`로 거절된다(로그에 남긴다).
- 저장 호출이 DB 하나의 연결을 직렬로 쓴다. 농장이 많아지거나 채집이 많을 때의 저장 처리량과 틱에 미치는 영향은 **측정하지 않았다(P4)**.
- 로그인한 사람은 임시 방(게스트 방)에 들어갈 수 없고, 게스트는 농장에 들어갈 수 없다.

## 13. 확인 방법

**터미널 (인메모리, DB 없이)**

```powershell
build\windows-local\Release\game_server.exe --port 7777 --log-level info
```

```powershell
build\windows-local\Release\game_client.exe --port 7777
```

`game_client`에서 `/register alice_01 password123`, `/login alice_01 password123`, `/create x`(내 농장 열기, 방 코드가 출력됨), `/profile`을 차례로 입력한다. 다른 터미널에서 `/register`와 `/login`을 한 뒤 `/join <코드> x`로 같은 농장에 들어갈 수 있다. 게스트(`--create --nick`)로는 농장에 들어갈 수 없다. 서버를 다시 켜면 인메모리라 계정이 사라진다.

**실제 MySQL (사용자가 실행, 비밀번호는 채팅 창에 쓰지 않는다)**

```powershell
$env:GAME_DB_PASSWORD = '비밀번호'
```

```powershell
build\windows-local\Debug\db_migrate.exe
```

```powershell
build\windows-local\Debug\account_mysql_test.exe
```

`db_migrate`는 002(계정)와 003(농장)을 적용한다. `account_mysql_test`는 시험 전용 테이블(`accounts_test`, `account_stats_test`, `farms_test`, `farm_structures_test`, `farm_players_test`)만 지우고 다시 만든다. 서버를 MySQL로 켜서 재시작해 보려면:

```powershell
build\windows-local\Release\game_server.exe --port 7777 --storage mysql
```

**Visual Studio 2022:** `build\windows-local\game_server_lab.sln`을 열고 `account_mysql_test`, `farm_integration_test`, `farm_persistence_test`, `farm_service_test`를 시작 프로젝트로 실행한다(DB 시험은 환경변수가 있어야 한다).

## 14. 알려진 한계 (설계 시점)

- TLS가 없어 비밀번호가 평문으로 전송된다(로컬 개발 한정).
- 서버가 갑자기 종료되면 마지막 저장 이후의 채집량을 잃는다.
- 농장은 닫혀 있는 동안 시간이 흐르지 않고, 자원 노드 상태는 저장하지 않는다.
- 농장 코드를 서버 시작 때 메모리에 모두 올리는 방식은 농장이 매우 많아지면 맞지 않는다.
- 서버 한 대, 한 DB 연결 기준이다. 저장 처리량의 상한은 재지 않았다.
