## 1. 프로젝트 한 줄 소개와 포지셔닝

**한 줄:** Boost.Asio 기반 C++20 게임 서버를 단계별로 만들고, 각 단계의 정확성과 성능을 **측정 기록으로 남긴** 프로젝트. Unreal 5.8 클라이언트까지 연결해 1~4인 협동 게임(방 코드 입장, 이동, 채집, 집 짓기)을 서버가 판정한다.

**기존 포트폴리오와의 차별점(`project.md`의 의도):** 이전에는 IOCP 서버, POCO, PostgreSQL, Protobuf, 2인 협동 게임 연동 경험이 있었다. 이번에는 (1) Boost.Asio로 OS 간 구현, (2) 서버가 게임 상태를 직접 소유, (3) **"최적화했다"가 아니라 측정 조건, 전후 수치, 한계까지 설명하는 결과**를 보여준다.

**이 프로젝트를 한 문장으로 요약하면 쓸 수 있는 메시지:**
"방 500개에서 불합격하던 서버의 병목을 측정으로 증명하고(전송 시스템 호출이 틱의 98%), 구조를 바꿔(소켓 입출력만 스레드 분리) 같은 조건에서 700개 이상까지 합격시켰다. 과정에서 내 결론을 두 번 철회했다."

## 5. 그림 재료

### 그림 1: 전체 구조

```
Unreal 클라이언트 (UE 5.8.4, C++ + 블루프린트)
      │  TCP  [길이 u32][메시지 ID u16][Protobuf]
      ▼
game_server (Boost.Asio, C++20)
  ├─ 소켓 입출력 구역: 연결별 strand, 읽기/송신 큐/쓰기  (--io-threads N개 스레드)
  │        ▲ dispatch │ dispatch ▼
  └─ 논리 구역 (스레드 1개): FrameDecoder, ChatRoom, GameService (20Hz 틱, 판정, 스냅샷)
                         └─ MySQL (채팅 기록)
```

원칙: **서버가 상태와 판정을 소유**한다. 클라이언트는 입력(이동 방향, 채집/건설 요청)만 보내고 서버가 계산한 값을 그린다.

## 6. 1~2단계 요약 (슬라이드 4)

- 프레임: `body_length`(u32) + `message_id`(u16) + Protobuf 본문, 모두 big-endian. 길이 허용 범위 2~65,536, 메모리 할당 **전에** 검사.
- 실패도 설계: 분할 수신, 한 번에 여러 프레임, 길이 0~1/초과, 알 수 없는 ID, 잘못된 Protobuf, 전송 중 연결 종료에서도 프로세스는 생존.
- 연결마다 송신 큐. 비동기 쓰기 버퍼는 쓰기 완료까지 유지. 느린 클라이언트는 송신 큐 한도(4 MiB) 초과 시 그 연결만 종료.
- 채팅: 입장/퇴장/방 전파/기록 조회. 채팅 로직(`ChatRoom`)은 소켓과 DB 구현을 모르고 인터페이스(`ChatClient`, `ChatRepository`)에만 의존 → 소켓 없이 가짜 연결로 시험.
- MySQL: Boost.MySQL(Asio 비동기), 연결 1개 + 작업 큐 직렬화, 모든 DB 호출에 제한 시간, 오류 시 재연결, 준비된 문장 바인딩, 번호 순서 마이그레이션. DB 호출이 `io_context`를 막지 않도록 설계.
- 한계: Windows 기준 완료, Linux 보류.

## 7. 3~4단계 성능 이야기 (핵심)

### 7.1 3단계: 측정 규칙과 도구의 한계

- 규칙: 합격 기준을 **측정 전에** 문서에 적는다. 생성기 포화 시 서버 결과로 인정하지 않는다. 비교는 한 번에 변수 하나, 조건당 3회, 매 실행 새 서버.
- 연결 5,000/10,000에서 p99 130~230 ms가 나왔지만 같은 실행에서 **부하 생성기가 포화**(CPU 103%+)였다 → "판정 불가"로 남기고 생성기를 다중 스레드로 개선.
- 재측정: Active **4,000연결(초당 4만 건) 3/3 합격**, 5,000은 1/3, 7,500부터 과부하. 서버 스레드 1개의 처리량 상한 약 4.5만/s. (`results/stage3/scaled.md`)
- 실험 1: `debug` 로그는 연결 500개(초당 5,000건)에서 서버 CPU 12.8% → 73.0%(응답당 약 5~6배). 부하 측정은 `info`. 실험 2: Nagle 끄기는 이득 없음 → 켬 유지. 통념을 수치로 확인한 사례.

### 7.2 4단계 첫 부하 측정

방 25~700개(방당 4명, 입력 초당 10번, 서버 20Hz 스냅샷). 500개 3/3 합격(서버 CPU 86.5%, 도착 간격 p99 53 ms, 입력 반영 p99 83 ms), 600개 불합격(누락 4~8%), 700개 불합격(누락 21~28%). 한계를 넘으면 **시뮬레이션 시간은 지키고 스냅샷이 줄어든다**(설계한 동작, 정합성 위반 0건). (`results/stage4/game-load.md`)

### 7.3 병목 증명

틱 단계별 계측 + 서버 밖 마이크로벤치로 비용이 소켓 송신 시스템 호출임을 확인(그림 2). 이 증거로 **직렬화 1회화, 객체 풀, 이동 최적화, 충돌 격자 분할**(각각 틱의 1% 안팎)을 버리고 송신 분리만 남겼다.

### 7.4 입출력 스레드 분리 (개선 후보 A)

- 설계: 게임 로직은 스레드 1개 그대로, 소켓 읽기/쓰기만 연결별 `strand`로 N개 스레드가 분담. 두 구역은 `dispatch`로만 넘나든다. 읽기는 한 번에 하나만 걸고 논리 처리가 끝난 뒤 재개(TCP 역압 유지). 직렬화는 로직 스레드에서 한 번.
- 결과: 그림 3. 같은 세션 기준 **분리 이전 400개까지 → 스레드 2개 600개 → 스레드 4개 700개 이상(상한 못 찾음)**.
- 대가: 서버 전체 CPU 약 25% 증가. 구조 자체의 비용이 있어 `IO0`는 분리 이전보다 약간 나쁘다(기본값은 0 유지).
- **`IO1`(스레드 1개)은 쓰면 안 되는 설정:** 누락 스냅샷 0인데 입력 반영 지연이 6~11초(500개 6.3초, 600개 11.1초). 도착 간격 p99만 봤다면 놓쳤을 문제를 합격 기준의 "입력 반영 지연"이 잡았다.
- 구현 중 버그: 입출력 스레드 4개로 통합 시험을 반복하자 프로세스가 가끔 죽음(소멸 순서: 풀과 서버가 먼저 사라진 뒤 남은 핸들러가 `Session`을 해제). 증거를 늘려가며 진단(버퍼 없는 출력, terminate 핸들러, CRT 보고)하고 세션의 풀 공유 소유 + 소멸 시 남은 핸들러 비우기로 수정. 60회 반복 실패 0.

## 8. 게임 서버 기능 (슬라이드 7)

- 방 만들기, 6자리 숫자 코드 입장(최대 4명), 방장 변경, 빈 방 삭제.
- 서버 판정 이동(속도 360 cm/s, 맵 5,000 x 5,000 cm), 20Hz 방 전체 스냅샷. 클라이언트는 방향만 보냄.
- 자원 채집: 서버가 나무 30개/돌 20개의 배치, 체력, 30초 재생, 거리(200 cm)와 쿨다운(0.5초)을 판정. 경쟁(4명이 마지막 체력을 동시에 침) 시험 포함.
- 집 짓기와 이동 충돌: 300x300 cm 집(목재 20, 석재 10, 5초 건설), 구조물과 살아 있는 나무/돌이 이동을 막고 벽을 따라 미끄러짐. 건설 가능 구역(맵 중앙)과 자원 구역 분리.
- 값(속도, 비용 등)은 **임의 기본값**이며 `PlayConfig`에서 바꾼다(기획 확정값이 아님).

## 9. "철회한 결론" 이야기 (슬라이드 9, 포트폴리오의 차별점)

1. 충돌, 구역, 속도 360이 들어간 뒤 재측정: 450개 합격/500개 불합격, 방당 CPU +15~27%로 보여 "충돌 탓"이라 해석.
2. 같은 세션에서 속도와 충돌을 번갈아 되돌려 보니 서버 CPU가 60.7/61.9/61.1/63.5%로 **동일**. 속도도 충돌도 원인이 아니었다. 같은 코드의 방 400개 CPU가 세션마다 60.7%, 70.7%, 84.3%로 달랐다(측정일 편차 20%+) → 결론 철회.
3. 이전/새 서버를 같은 세션에서 비교하려던 실험은 사용자가 게임을 하며 CPU를 써서 이전 서버마저 불합격 → **무효 처리**(원본은 남기고 결론에 쓰지 않음).
4. 바뀐 절차: 실행 전 PC CPU 5초 평균 10% 이하일 때만 시작, 진행 기록, 조건 번갈아 실행, 의심 실행을 임의로 빼지 않고 한계에 기록.

→ 이 이야기의 의미: **틀린 결론을 지우지 않고 "정정"으로 남겼고, 그 경험이 측정 절차를 바꿨다.**

## 10. Unreal 클라이언트와 MCP (슬라이드 13)

### 10.1 클라이언트가 하는 일

메뉴(방 만들기/코드 입장) → 방 안 이동(WASD) → 스냅샷 보간 → 탑뷰 카메라 → 자원 채집(`E`) → 집 짓기(`B` 건설 모드, 미리보기, 클릭 건설) → HUD(UMG). 엔진은 5.4.4에서 먼저 확인한 뒤 5.8.4로 올림.

### 10.2 MCP란 무엇이고 무엇을 맡겼나

- **Unreal MCP:** UE 5.8에 들어 있는 Epic의 실험 기능 플러그인(`ModelContextProtocol`, `EditorToolset`). 에디터가 로컬 HTTP(`127.0.0.1:8000/mcp`)로 MCP 서버를 열고, Claude Code가 프로젝트의 `.mcp.json`으로 연결해 에디터를 조작한다. 에디터 상태, 액터, 에셋, 블루프린트, 레벨, 머티리얼, 메시, 오브젝트 프로퍼티 등의 툴셋이 있다.
- **책임 분담(핵심 설계 규칙): 로직은 전부 C++, 에디터에서만 되는 일은 MCP.** 이유: (1) C++ 로직은 진짜 서버에 붙여 자동 시험·변형 검증이 가능, (2) 에셋은 diff로 검토할 수 없는 바이너리(Git LFS)라서 로직이 없어야 안전, (3) 접점이 작음(`UCLASS(Abstract)` 부모, `BindWidget` 이름, `UPROPERTY` 배열).
- **작업 순서(조각마다 동일):** S0 서버 C++(시험·변형 검증) → S1 Unreal C++(에디터 닫음, 빌드를 위해) → S2 **MCP 세션**(에디터 엶) → S3 사람이 에디터에서 확인. C++ 빌드는 에디터가 꺼져 있어야 하고(Live Coding이 막음) MCP는 에디터가 켜져 있어야 해서 번갈아 한다.
- **MCP를 위해 C++에서 미리 해 둔 것:** 새 위젯은 `BindWidgetOptional`로 만들어 에셋이 없어도 빌드가 깨지지 않게 함, 에셋이 없으면 엔진 기본 큐브와 색 값으로 대체되게 함.

### 10.3 MCP 세션이 만든 것

| 조각 | 한 일 |
| --- | --- |
| 메뉴/기반 | `L_Menu`, `BP_MenuGameMode`, `BP_YongPlayer`, `BP_YongRoomGameMode`, `WBP_MainMenu`/`WBP_HUD` 위젯 트리, 머티리얼 3개, `L_Farm`에 Kenney 메시 소품 배치 |
| 자원 채집 | `BP_ResourceTree`, `BP_ResourceRock`(메시 후보, 충돌 없음, cm 크기 보정), `L_Farm`에 손으로 놓은 나무/돌 제거(서버가 위치를 정하므로), HUD 인벤토리/힌트 위젯, 게임 모드 연결 |
| 집 짓기 | `BP_House`, `BP_BuildGhost`, 머티리얼 3개(집, 건설 가능, 건설 불가), 게임 모드의 클래스 연결, HUD 건설 비용/안내 위젯 |

### 10.4 MCP 사용 시 지킨 안전 규칙

- 인증 없는 로컬 HTTP 서버라서 `127.0.0.1`에만 열고, 쓰지 않을 때는 에디터를 닫는다(다른 프로그램도 이 포트로 에디터를 조작할 수 있다는 점을 문서화).
- 애셋을 만들기 **전에** Git LFS 설정을 커밋.
- MCP가 한 일은 사람이 PIE로 확인하기 전에는 "완료"로 적지 않는다.

### 10.5 클라이언트 검증 방법

- 커맨들릿 시험(`-run=GameClientSpike -mode=...`, 화면 없이): 진짜 서버에 접속해 판정. 모드별 건수 `interp` 21, `real` 53, `subsystem` 19, `gather` 40, `subsystem-gather` 25, `buildrules` 25, `build` 35, `ui` 21 등.
- **"걸어가서 친다"가 시험 시나리오:** 서버 판정을 흉내 내지 않고 실제로 이동 입력을 보내 나무까지 걸어가 목재 20/석재 10을 모은 뒤 집을 지음. 집 한가운데로 걸어도 몸이 발자국 안에 들어가지 못하는지까지 확인.
- 가짜 서버(`fake_server.py`)로 나쁜 입력(1바이트씩 쪼갠 프레임, 규약 밖 길이, 해석 못 하는 스냅샷) 시험.
- 변형 검증으로 시험의 구멍 확인. 처음 만든 "왕복 지연" 시험이 송신 분리 버그를 **못 잡아서** `send` 모드를 추가한 사례(고친 코드 20/20, 되돌린 코드 0/20), 변형 도구가 한글 로그를 잘못 읽어 거짓으로 "잡힘"이라 보고한 사례(통과 건수 0으로 알아차림).
- 사람 확인: 에디터 두 창(Play Standalone)으로 서버에 접속해 한 방에 여러 명이 보이는 것을 확인.

## 11. 겪은 문제 모음 (슬라이드 14 또는 부록)

- 서버: 소멸 순서 버그(7.4), 집계 구간 경계 오류(측정 뒤 연결 정리 구간이 섞여 틱 건너뜀이 잘못 높게 나옴 → 클라이언트 최대 간격과 안 맞아서 알아차림), PowerShell이 `300,450`을 `300450`으로 읽어 잘못된 값으로 한 번 실행(곧바로 중단, 기록 삭제 후 재실행).
- Unreal: 5.4의 MSVC/Protobuf 빌드 문제(5.8에서 우회 3가지 제거), Abseil `verify` 매크로 충돌, `.pb.cc` 합치면 오류, PowerShell `-host=127.0.0.1`이 점에서 쪼개짐(처음엔 Unreal 파서 탓으로 오해), `AllToolsets` 플러그인 때문에 종료 코드가 항상 1이라 로그로 판정.
- 시험: 채집 변형 20개 중 2개, 건설/충돌 변형 30개 중 3개를 처음에는 놓침(둘째 목록의 1개는 동등 변형).

## 12. 한계와 후속 과제 (반드시 같이 말할 것)

- **모든 성능 수치는 Windows, Release, 한 PC의 루프백**(서버와 부하 생성기가 코어를 나눠 씀, Ryzen 5 5600, 12 논리 프로세서). 실제 네트워크와 다를 수 있다. **Linux 결과는 없다.**
- 입출력 스레드 4개의 **상한을 찾지 못했다**(사전 규칙이 700개까지만 허용).
- 방 700개 `IO2` 1회차와 방 400개 `IO0`/`IO1` 일부 실행은 측정 중 PC 부하가 섞였을 가능성이 있어 **확정 결과로 읽지 않는다.** 500/600개는 3회가 같은 방향이라 결론이 흔들리지 않는다.
- 기본 `--io-threads`는 0이다. 스레드 수 선택 기준과 "느린 연결에 낡은 스냅샷이 쌓이는 문제"(스냅샷 대체/건너뛰기)는 구현하지 않았다.
- Unreal: 노드/구조물 액터의 모양, 건설 모드 마우스 입력, HUD 표시는 컴파일까지만 자동 확인(월드가 필요). 3~4명 동시 접속과 패키징한 빌드는 시험하지 않음. 채팅 메시지는 Unreal에서 보낸 적 없음. 미니맵(`YongMinimapWidget`)은 Unreal 저장소에 **미커밋·미시험**이라 성과로 쓰지 않는다.
- 게임 규칙 값은 임의 기본값이며 기획 확정값이 아니다.

## 13. 말하면 안 되는 주장

- "방 500개에서 700개로 40% 향상"처럼 단일 비율로 요약하지 않는다. 첫 측정의 500개(충돌 이전 서버)와 같은 세션 비교의 `PRE` 500개 불합격이 달랐다. **같은 세션 안에서의 비교**로만 말한다: 분리 이전 400개 → 스레드 2개 600개, 스레드 4개 700개 이상.
- "700개가 한계" 또는 "스레드 4개가 최적"이라고 하지 않는다(상한 미탐색).
- "CPU가 늘지 않았다"고 하지 않는다(약 25% 증가).
- "Linux에서도 동작/측정했다"고 하지 않는다.
- "충돌이 CPU를 늘렸다"를 쓰지 않는다(철회됨). 쓴다면 철회 사례로만.
- 초당 처리량이나 접속자 수를 실서비스 용량처럼 말하지 않는다(루프백, 같은 PC, 합격 기준 한정).
- Unreal MCP를 "완전 자동으로 게임을 만들었다"고 표현하지 않는다. 로직은 C++, MCP는 에셋/레벨/위젯 배치였고 사람이 확인했다.
- 개발 도구(Claude Code, Unreal MCP)를 어떻게 소개할지는 본인이 정한다. 이 프로젝트의 작업 방식 자체가 "AI 에이전트 + 에디터 자동화를 검증 체계(시험, 변형 검증, 문서)로 통제한 사례"라는 이야기가 될 수 있다.

## 15. 슬라이드를 만들 때 쓸 쉬운 설명 (비전문 독자용)

- **strand:** 같은 연결의 일이 동시에 겹치지 않게 순서를 보장하는 Boost.Asio의 직렬 실행 구역.
- **틱:** 서버가 게임 상태를 한 번 갱신하는 주기(20Hz = 초당 20번).
- **스냅샷:** 서버가 방 전체의 현재 위치를 보내는 메시지.
- **p99:** 100번 중 99번은 이 시간 안에 끝난다는 값(꼬리 지연).
- **루프백:** 서버와 클라이언트가 같은 PC 안에서 네트워크 카드를 거치지 않고 통신하는 방식.
- **변형 검증:** 코드를 일부러 망가뜨려 시험이 그 버그를 잡는지 확인하는 방법(시험의 시험).
