# 2단계: 채팅과 MySQL (진행 기록)

> 상태: **Windows 기준 완료.** 2-0~2-5를 마쳤고, 실제 MySQL(26.10.0)을 대상으로 한 `chat_mysql_test` 13개가 모두 통과했다. 남은 일은 Linux 확인(보류)뿐이다. 목표와 완료 기준은 [project.md](../project.md#2단계-채팅과-mysql), 프로토콜은 [protocol-chat.md](protocol-chat.md).

## 목표와 완료 기준

여러 클라이언트가 같은 방에서 메시지를 주고받고, 필요한 대화 기록을 MySQL에 저장·조회한다.

완료 기준: 다중 사용자 전파, 재접속 후 기록 조회, DB 중단·복구 시나리오를 확인한다. 처음에는 단일 서버·단일 방이다.

## 결정 기록

| 결정 | 이유 | 검토한 대안 |
| --- | --- | --- |
| MySQL 드라이버: **Boost.MySQL** (`boost-mysql`) 먼저 시도 | Asio 비동기를 그대로 써서 DB 호출이 `io_context` 안에서 논블로킹이다. 스레드를 새로 만들지 않아 1단계의 단일 스레드 전제가 유지된다. | MySQL Connector/C++ (동기식이라 DB 전용 워커 스레드와 결과 전달 설계가 필요, 이 단계에서 처음 스레드가 등장) |
| 저장 실패 정책: **저장 성공 후 전파**, 실패 시 보낸 사람에게 오류 응답 | 기록에 없는 메시지는 존재하지 않는다는 일관성. 구현이 단순하다. | 먼저 전파하고 비동기 저장 (빠르지만 실시간으로 본 메시지가 기록에 없을 수 있음) |
| 방 단위로 저장을 직렬화 | 같은 방의 전파 순서를 `message_id` 순서와 일치시킨다. | 병렬 저장 (처리량은 높지만 순서가 뒤바뀔 수 있음) |
| 업무 규칙 위반은 오류 코드 응답 + 연결 유지, 프로토콜 위반은 연결 종료 | 닉네임 중복 같은 일상적 오류로 연결을 끊을 이유가 없다. | 모든 오류에서 연결 종료 (1단계 방식) |
| MySQL 서버는 Windows에 직접 설치 | 이 PC에 Docker가 없다. | Docker Desktop 설치 |

드라이버 결정은 **Boost.MySQL로 확정**했다. Windows에서 빌드(OpenSSL 3.6.5 포함)와 실제 MySQL 26.10.0 접속·질의를 확인했다. 두 방식의 비교(DB 호출 중 다른 연결의 지연)는 3단계 실험 후보다.

설계 원칙: 채팅 로직은 `ChatRepository`(저장소 인터페이스)에만 의존한다. 자동 테스트는 가짜 저장소로 대부분 검증하고, 실제 MySQL을 쓰는 테스트는 별도로 분리해 서버가 없으면 건너뛴다. 그래야 DB 없이도 테스트가 돌고, "DB 중단" 시나리오도 가짜 저장소에 실패를 주입해 재현할 수 있다.

## 2-2 결과: 인메모리 채팅

### 구성

| 위치 | 역할 |
| --- | --- |
| `proto/chat.proto` | 채팅 메시지와 `ResultCode` 정의 |
| `src/chat/chat_rules.*` | 닉네임/메시지 검증 규칙. 소켓과 방 상태를 모르는 순수 함수 |
| `src/chat/chat_repository.h` | 저장소 인터페이스. 결과는 반환값이 아니라 핸들러로 돌려준다 |
| `src/chat/in_memory_chat_repository.*` | 메모리 저장소. 테스트용 장애·지연 주입(`SetFailing`, `SetDelay`) 지원 |
| `src/chat/chat_client.h` | 방이 보는 "연결"의 인터페이스. `Session`이 구현한다 |
| `src/chat/chat_room.*` | 방 하나: 접속자, 입장/퇴장, 저장 대기열(직렬화), 시간 제한, 전파, 기록 조회 |
| `src/server/session.*` | 요청 5종을 파싱해 방에 넘기고, 방이 보내는 메시지를 송신 큐에 넣는다 |
| `src/client/chat_client.cpp` | 직접 실험하는 대화형 클라이언트 |

### 설계에서 정한 것

- **방은 저장소와 연결의 인터페이스만 안다.** 그래서 소켓 없이 가짜 연결로 방 로직을 단위 테스트하고, 2-3에서 `ChatRepository` 구현만 MySQL로 바꾸면 된다.
- **저장은 방 단위로 한 번에 하나씩, 도착 순서대로** 한다. 저장 시간이 서로 달라도 전파 순서가 `message_id` 순서와 같다.
- **제한 시간(기본 3초)을 넘으면 실패로 응답**하고 다음 채팅으로 넘어간다. 뒤늦게 도착한 저장 결과는 버린다(저장소에는 반영될 수 있음).
- **전파 도중 연결이 닫혀도 순회가 깨지지 않도록** 수신자 목록의 복사본으로 보낸다.
- **방은 연결을 약한 참조로만 든다.** 연결이 방에서 빠지지 않고 사라져도 건너뛴다.
- 저장소가 콜백을 항상 `io_context` 스레드에서 호출하므로 방에는 잠금이 없다.

### 실제 서버에서 확인

`game_server`와 `chat_client` 두 개로 입장 알림, 한글 대화 전파, 기록 조회, 퇴장 알림, 이중 입장 거부를 직접 확인했다.

### 알려진 제한

- 기록은 서버를 끄면 사라진다(메모리 저장소). 2-3에서 MySQL로 바꾼다.
- 방 하나, 접속자 목록은 배열이라 입장/퇴장이 접속자 수에 비례한다(전파도 어차피 비례). 큰 방은 3단계에서 측정한다.
- 보이지 않는 문자(폭이 없는 공백 등)는 막지 않는다. 앞뒤 공백은 스페이스, U+00A0, U+3000만 공백으로 본다.
- 저장 제한 시간 뒤에 저장이 늦게 반영될 수 있다(결과 불명). 문서화만 했고 막지 않는다.
- 닉네임 대소문자는 구분한다. "Alice"와 "alice"는 다른 닉네임이다.
- 요청 빈도 제한이 없다. 한 사용자가 채팅을 쏟아내면 저장 대기열 한도(256)와 송신 큐 한도로만 막힌다.

## 2-3 구성: MySQL 저장소

| 위치 | 역할 |
| --- | --- |
| `db/migrations/001_create_chat_messages.sql` | 채팅 테이블. utf8mb4를 명시하고 `id`는 AUTO_INCREMENT |
| `src/tools/db_migrate.cpp` | 마이그레이션 적용 도구. 번호 순서대로 적용하고 `schema_migrations`에 기록, 적용한 번호는 건너뜀 |
| `src/chat/mysql_chat_repository.*` | `ChatRepository`의 MySQL 구현 (Boost.MySQL, 코루틴) |
| `src/common/db_credentials.*` | DB 비밀번호를 환경변수/파일에서 읽는 도우미 |
| `tests/chat_mysql_test.cpp` | MySQL 대상 테스트. 비밀번호가 없으면 건너뜀 |

### 설계에서 정한 것

- **DB 호출이 네트워크 I/O를 막지 않는다.** 비동기 API를 코루틴으로 써서 DB 응답을 기다리는 동안에도 같은 스레드가 다른 연결을 처리한다. 스레드를 새로 만들지 않았다.
- **연결 하나, 작업은 큐로 직렬화.** MySQL 연결은 한 번에 작업 하나만 처리할 수 있는데 방은 저장과 기록 조회를 동시에 요청하기 때문이다.
- **모든 DB 호출(연결, 문장 준비, 실행)에 제한 시간(기본 1.2초)** 을 건다. 응답 없는 DB가 큐 전체를 막지 않는다.
- **오류가 나면 연결을 버린다.** 다음 요청이 새로 연결하므로 DB가 내려갔다 올라와도 서버를 다시 시작할 필요가 없다.
- **쓰기는 자동 재시도하지 않는다.** 연결이 끊긴 순간 서버가 이미 반영했는지 알 수 없어서, 재시도하면 같은 메시지가 두 번 저장될 수 있다.
- **쿼리는 모두 준비된 문장에 값을 바인딩한다.** 사용자 입력이 SQL 문자열에 섞이지 않는다. 테이블 이름만 문자열로 넣는데 영문/숫자/밑줄만 허용한다.
- **비밀번호는 명령줄로 받지 않는다.** 환경변수 `GAME_DB_PASSWORD` 또는 `GAME_DB_PASSWORD_FILE`(파일 경로)로만 받고, 로그에 출력하지 않는다.
- **운영 데이터를 건드리지 않는 테스트.** 테스트는 `chat_messages_test` 테이블만 쓰며, 실제 마이그레이션 SQL에서 이름만 바꿔 만든다.

### 실행

프로젝트 폴더에서 마이그레이션을 적용한다.

```bash
.\build\windows-local\Debug\db_migrate.exe
```

서버를 MySQL 저장소로 실행한다.

```bash
.\build\windows-local\Debug\game_server.exe --port 7777 --storage mysql
```

### DB 없이 확인한 것 (Windows, Debug)

- `--storage mysql`인데 비밀번호가 없으면 안내와 함께 종료 코드 2로 끝난다.
- DB에 연결할 수 없는 상태로 서버를 띄워도 서버는 동작한다. 입장과 Ping은 정상이고, 채팅과 기록 조회는 `STORAGE_FAILURE`로 빠르게 응답한다. 시작 로그에 DB 연결 실패가 남고, 비밀번호는 로그에 나오지 않는다.
- 실제 드라이버로 닫힌 포트에 연결하면 약 1.2초 만에 읽을 수 있는 오류로 돌아온다.
- 위험한 테이블 이름(공백, 백틱, 세미콜론, 한글 등)은 거부한다.

### MySQL 대상 테스트 (13개 통과)

`chat_mysql_test` 13개(DB가 필요한 11개 + 필요 없는 2개)가 실제 MySQL 26.10.0에서 모두 통과했다. 첫 실행에서는 2개가 실패했는데(`bad_value_access`), 연결을 강제로 끊는 시험의 **테스트 도우미**가 MySQL이 돌려주는 연결 번호의 숫자 타입을 하나로 단정했기 때문이었다. 저장소 코드의 문제가 아니었고(저장·조회 등 본체 테스트는 첫 실행에서도 통과), 숫자 타입을 가리지 않고 읽도록 도우미를 고친 뒤 13개가 모두 통과했다.

| 테스트 | 확인하는 것 |
| --- | --- |
| 저장 후 조회 | 한글, 이모지, 따옴표, 백슬래시, `'; DROP TABLE ...` 같은 문장이 값 그대로 저장되고 조회됨 |
| 최근 N개 | 마지막 N개를 오래된 순으로 |
| 빈 테이블 | 빈 목록 |
| 동시 요청 | 저장 30건과 조회 10건을 동시에 요청해도 모두 성공, 번호는 중복 없이 증가 |
| 연결 강제 종료 | DB가 연결을 끊으면 그 요청만 실패하고 다음 요청부터 복구, 끊긴 사이의 메시지는 저장되지 않음 |
| 연결 재설정 | 연결을 버린 뒤 다음 요청이 새로 연결 |
| 잘못된 비밀번호 | 거부되고 오류 메시지에 비밀번호가 없음 |
| 서버 재시작 | 서버를 껐다 켜도 기록이 남고 번호가 이어서 증가 |
| 서버 + DB 장애 | 연결이 끊기면 `STORAGE_FAILURE`, Ping 정상, 복구 후 서버 재시작 없이 정상 |
| DB 없이 시작 | 입장은 되고 채팅만 빠르게 실패 |

### 알려진 제한

- DB 연결은 하나다. 연결 풀은 병목이 관측되면 3단계에서 비교한다.
- 제한 시간 뒤에 저장이 늦게 반영될 수 있다(결과 불명). 방의 제한 시간(3초)과 드라이버의 단계별 제한 시간(1.2초)은 별개이며, 연결·준비·실행이 모두 느리면 한 요청이 방의 제한 시간을 넘길 수 있다.
- 마이그레이션 도구는 이미 적용한 파일의 내용이 바뀌었는지는 검사하지 않는다.
- 서버를 시작할 때 테이블이 있는지는 확인하지 않는다. 테이블이 없으면 첫 요청이 "문장 준비 실패" 메시지와 함께 `STORAGE_FAILURE`가 된다.

## MySQL 서버 준비 (직접 설치)

이 PC에는 MySQL과 Docker가 없다. 설치 프로그램 실행, 라이선스 동의, 비밀번호 설정이 필요해서 직접 진행해야 한다.

1. https://dev.mysql.com/downloads/mysql/ 에서 **MySQL Community Server**(LTS 계열 권장)의 Windows MSI 설치 파일을 받아 설치한다.
2. 설치 중 포트는 3306, Windows 서비스로 실행, root 비밀번호를 정한다. (개발 전용 PC의 개발용 서버임을 전제한다.)
3. 서비스가 켜져 있는지 확인한 뒤, 이 프로젝트 전용 데이터베이스와 계정을 만든다. root로 채팅 서버를 돌리지 않는다.

```sql
CREATE DATABASE game_chat CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'game'@'localhost' IDENTIFIED WITH caching_sha2_password BY '여기에_비밀번호';
GRANT ALL PRIVILEGES ON game_chat.* TO 'game'@'localhost';
```

4. 접속을 확인한다. 비밀번호는 환경변수로 전달하며 명령줄이나 파일에 적지 않는다.

```bash
$env:GAME_DB_PASSWORD = '여기에_비밀번호'
.\build\windows-local\Debug\mysql_check.exe --user game --db game_chat
```

성공하면 서버 버전, 문자 집합, 정렬 규칙이 출력된다.

**계정의 인증 플러그인은 `caching_sha2_password`여야 한다.** Boost.MySQL은 `caching_sha2_password`와 `mysql_native_password`만 지원한다. 계정이 `sha256_password` 같은 다른 플러그인을 쓰면 `mysql_check`가 "The user employs an authentication plugin not known to this library"로 실패한다.

**같은 오류가 "계정이 아예 없을 때"도 나온다.** MySQL은 없는 계정에 대해서도 어떤 계정이 있는지 알아내지 못하도록 그럴듯한 가짜 인증 플러그인을 알려 준다. 그래서 이 오류만으로는 계정의 플러그인이 잘못된 것인지 계정이 없는 것인지 구분되지 않는다. 먼저 MySQL에 root로 접속해 계정이 있는지 본다.

```sql
SELECT user, host, plugin FROM mysql.user WHERE user = 'game';
```

행이 없으면 계정이 없는 것이다(위의 "계정 만들기" 참고). 행이 있는데 `plugin`이 다르면 다음으로 바꾼다. `host`는 표에 나온 값을 쓴다.

```sql
ALTER USER 'game'@'localhost' IDENTIFIED WITH caching_sha2_password BY '여기에_비밀번호';
```

적용됐는지는 MySQL에서 확인한다. `plugin` 열이 `caching_sha2_password`여야 한다. 같은 이름의 계정이 호스트별로 여러 개 있을 수 있으므로(`localhost`, `%`, `127.0.0.1`) 모든 행을 본다.

```sql
SELECT user, host, plugin FROM mysql.user WHERE user = 'game';
```

확인된 환경: MySQL Community Server 26.10.0(Windows 서비스 `MySQL2610`, 포트 3306). 서버가 처음 알려주는 기본 인증 플러그인은 `caching_sha2_password`다.

## 열린 문제

- 저장 요청이 시간 초과로 실패했지만 실제로는 DB에 반영된 경우의 처리([protocol-chat.md](protocol-chat.md)의 "알려진 불확실성").
- DB 연결을 1개로 쓸지 풀을 둘지. 처음에는 연결 1개로 시작하고, 병목이 관측되면 3단계에서 비교한다.
