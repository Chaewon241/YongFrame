# 3단계: 수용 규모와 병목 검증 (진행 기록)

> 상태: **기준 측정과 확장 측정 완료.** 기준 측정은 Active 2,000연결까지 합격이었고 그 이상은 생성기 포화로 판정하지 못했다. 생성기를 다중 스레드로 바꿔 다시 재니 **Active 4,000연결(초당 4만 건)까지 3회 모두 합격, 5,000부터 불합격이 섞이고 7,500 이상은 서버 스레드 1개가 포화**됐다. 비교 실험 1(로그 레벨)과 2(Nagle)도 끝났고, 다음은 실험 3(스레드 수)이다. 결과는 [baseline.md](../results/stage3/baseline.md), [scaled.md](../results/stage3/scaled.md), [exp1-loglevel.md](../results/stage3/exp1-loglevel.md), [exp2-nodelay.md](../results/stage3/exp2-nodelay.md). 이 문서의 합격 기준은 측정 **전에** 확정했고 결과를 본 뒤에는 바꾸지 않는다. 바꿔야 한다면 바꾸는 이유와 함께 이 문서에 따로 기록한다.

## 질문

"이 서버는 클라이언트를 몇 명 받는가?"를 **워크로드, 합격 기준, 측정 환경을 붙여서** 답한다. "몇 % 빨라졌다"는 주장은 같은 조건에서 한 번에 한 변수만 바꾼 비교로만 한다.

## 범위 결정 (속도를 위해 좁힌 것)

- **측정은 Windows만 한다.** Linux는 보류 중이므로 이 단계의 숫자는 Windows 결과라고 명시한다. Linux 결과가 생기면 따로 낸다(합치지 않는다).
- **비교 실험은 세 가지로 제한한다.** 병목이 관측되기 전에는 늘리지 않는다.
- **메모리 풀은 하지 않는다.** 할당이 병목이라는 증거가 나오면 그때 추가한다.
- 부하 생성기는 처음에 스레드 1개였고, 기준 측정에서 Active 5,000 이상을 감당하지 못해 `--threads N`(스레드마다 자기 `io_context`와 연결 묶음)로 확장했다. 생성기가 먼저 포화되면 그 사실을 결과에 표시한다(아래 합격 기준의 "생성기 포화"). 스레드가 여러 개일 때 CPU 기준은 **스레드당 평균** 80%다.

## 측정 환경과 알려진 한계

- 서버와 부하 생성기가 **같은 PC**에서 돈다(루프백). 두 프로세스가 CPU와 메모리를 나눠 쓰므로 절대 수치는 실제 네트워크 환경보다 유리하게 나올 수 있다. 서로 다른 머신에서의 측정은 하지 않았다.
- 루프백에서 한 서버 포트로 만들 수 있는 연결은 윈도우의 임시 포트 범위(기본 약 16,000개)에 묶인다. 그보다 큰 연결 수는 이 환경에서 측정하지 않는다.
- 서버 설정: 빌드는 Release, 로그 레벨은 실험 변수가 아니면 `info`, 상세 패킷 로그 끔, `io_context` 스레드 1개(실험 3 제외).
- 환경(OS, CPU, RAM, 컴파일러, 라이브러리 버전)은 결과 기록마다 함께 남긴다.

## 워크로드

| 워크로드 | 정의 | 무엇을 보는가 |
| --- | --- | --- |
| **Idle** | 연결을 맺고 5초마다 Ping 1건 | 접속을 유지하는 비용: 메모리, 연결 성공률 |
| **Active** | 연결마다 초당 10건의 Ping, payload 64바이트 | 실제 메시지 처리 능력: 지연, 처리량, 오류 |

요청 하나는 부하 생성기가 `request_id`와 payload를 만들어 보내고, 서버가 그대로 돌려준 응답을 요청마다 대조한다(불일치도 오류로 센다). 요청은 응답을 기다리지 않고 정해진 시각에 보낸다(열린 루프). 응답이 늦어도 보내는 간격을 늦추지 않아야 서버가 느려졌을 때 지연이 숨겨지지 않는다.

## 합격 기준 (측정 전에 확정)

**최대 안정 연결 수** = 아래를 **모두** 만족하는 가장 큰 동시 연결 수.

| 항목 | 기준 | 비고 |
| --- | --- | --- |
| 연결 성공률 | 99.9% 이상 | 시도한 연결 중 성공한 비율 |
| 오류율 | 0.1% 이하 | (불일치 + 응답 없음 + 전송 오류) / 측정 구간에 보낸 요청 |
| 왕복 지연 p99 | 50 ms 이하 | 루프백 기준. p50, p95, 최대도 함께 기록 |
| 메모리 | 지속 증가 없음 | 서버 작업 집합(working set)의 측정 구간 후반 1/3 평균이 전반 1/3 평균의 1.05배 이하 |
| 생성기 포화 아님 | 보내기 예정 시각 대비 실제 지연 p99가 5 ms 이하, 생성기 CPU가 한 코어의 80% 이하 | 이를 넘으면 그 측정은 **서버의 한계가 아니라 생성기의 한계**로 보고 합격/불합격을 판정하지 않는다 |

## 절차

1. 같은 커밋·같은 Release 빌드로 측정한다. 빌드 설정과 커밋을 기록한다.
2. 연결 수를 100, 500, 1,000, 2,000, 5,000, 10,000으로 올린다. 한 단계마다 새 서버 프로세스로 시작한다.
3. 한 단계는 연결 수립(속도 제한) → 워밍업 5초(기록하지 않음) → 측정 30초 → 종료 순서다.
4. 각 조건을 **3회 반복**하고 중앙값과 최소·최대를 기록한다. 실패한 반복도 숨기지 않는다.
5. 평균 지연만 보지 않고 p50, p95, p99, p99.9, 최대를 남긴다. 처리량과 성공률을 함께 표시한다.
6. 보낸 요청 수와 받은 응답 수를 대조한다.
7. 서버와 생성기의 CPU, 메모리를 함께 기록한다.

## 비교 실험 (한 번에 한 변수, 기준 버전으로 되돌려 재측정)

| 번호 | 변수 | 비교 | 함께 볼 비용 |
| --- | --- | --- | --- |
| 1 | 로그 레벨 | `debug`(요청마다 로그) vs `info` | CPU, 지연. 로그가 얼마나 비싼지 보여 준다 |
| 2 | 송신 방식 | `TCP_NODELAY` 켬(즉시 송신) vs 끔(운영체제가 모아 보냄, Nagle 알고리즘) | 지연, 처리량 |
| 3 | `io_context` 스레드 수 | 1 vs 2 vs 4 (소켓과 방에 strand 적용) | 지연, 처리량, CPU, 복잡도 |

기준은 "로그 `info`, `TCP_NODELAY` 켬, 스레드 1개"다. 실험 3은 서버 코드(strand)를 바꾸는 작업이 필요하므로 실험 1, 2를 먼저 한다. 차이가 측정 오차 안에 있으면 단순한 쪽(기준)을 유지한다.

### 실험 1 계획: 로그 레벨 (측정 전에 확정)

- **질문:** 요청마다 로그를 남기는 `debug`는 `info`에 비해 지연, 서버 CPU, 최대 안정 연결 수를 얼마나 바꾸는가.
- **바꾸는 변수:** 서버 `--log-level debug` vs `info` 하나뿐. 그 밖의 서버 설정, 빌드(Release), 생성기(스레드 4개), 워크로드(Active, 연결당 초당 10건, payload 64B, 워밍업 5초, 측정 30초)는 같다.
- **조건:** 연결 1,000 / 2,000 / 3,000 / 4,000. 조건마다 3회, 매 실행 새 서버 프로세스. 기준 측정 값을 재사용하지 않고 **같은 세션에서 `info`도 다시 잰다.** 컴퓨터 상태가 시간에 따라 변하는 영향을 줄이기 위해 두 레벨을 번갈아 실행하고(회차마다 먼저 하는 쪽을 바꾼다) 같은 회차끼리 짝지어 본다.
- **서버 출력:** 두 레벨 모두 서버의 표준 출력을 **파일로 리디렉션**한다(콘솔 창에 직접 쓰는 비용은 별도이며 이 실험에 포함하지 않는다). `debug`는 요청마다 한 줄을 남기고 줄마다 flush한다. 실행 후 로그 파일 크기를 기록한다.
- **차이를 인정하는 기준:** 지표(p99, 서버 CPU)별로 `debug`의 **중앙값이 `info` 3회의 최솟값~최댓값 범위 밖**이면 차이가 있다고 본다. 범위 안이면 측정 오차 안이므로 "차이를 확인하지 못했다"고 쓴다. 합격 판정(최대 안정 연결 수)은 기존 합격 기준을 그대로 쓴다.
- **결정 규칙:** 차이가 오차 안이면 로그 레벨 기본값을 바꾸지 않는다. `debug`가 더 비싸더라도 기본값(`debug`)을 그대로 둔다. 다만 부하 실험에서는 `info` 이상을 쓴다는 기존 규칙(validation.md 1절)의 근거 수치로 쓴다.
- **추가 조건 (1차 매트릭스 후 추가, 기준은 그대로):** 1차(1,000~4,000연결)에서 `debug`가 가장 낮은 부하에서도 측정 구간에 응답을 하나도 받지 못해 비용을 수치로 비교할 수 없었다. 그래서 같은 절차로 **100 / 250 / 500연결**(초당 1,000 / 2,500 / 5,000건)을 추가로 잰다. 이 조건은 1차 결과를 본 뒤에 추가했다는 사실을 결과 기록에 적는다.
- **원인 주장 금지:** CPU 증가가 로그 때문이라고 말하려면 `info`와의 차이가 위 기준을 넘어야 하며, 세부 원인(문자열 조립, flush, 파일 쓰기 중 무엇이 큰가)은 이 실험으로는 나누지 않는다.

### 실험 2 계획: TCP_NODELAY (측정 전에 확정)

- **질문:** 서버 소켓의 `TCP_NODELAY`를 끄면(운영체제가 작은 패킷을 모아 보내는 Nagle 알고리즘이 동작) 지연과 처리량이 켠 상태(기준)와 달라지는가.
- **바꾸는 변수:** 서버 `--tcp-nodelay on` vs `off` 하나뿐. 부하 생성기 쪽 소켓은 항상 `TCP_NODELAY`가 켜져 있다(생성기는 바꾸지 않는다). 그 밖의 서버 설정(로그 `info`, 스레드 1개, 인메모리), 빌드(Release), 생성기(`--threads 4`), 워밍업 5초, 측정 30초, payload 64B는 같다. 매 실행 새 서버 프로세스.
- **워크로드와 조건 (두 가지):**
  - A. 기준 Active(연결당 초당 10건): 연결 1,000 / 2,000.
  - B. 연결당 빈도가 높은 Active(연결당 초당 100건): 연결 100 / 200 (초당 1만 / 2만 건). Nagle은 한 연결에서 앞선 데이터의 ACK를 기다리는 동안만 작동하므로 연결당 요청 간격이 짧을수록 영향이 드러날 가능성이 있어 포함한다. 이 B는 기준 워크로드(연결당 초당 10건)와 다른 **추가 워크로드**이며 연결당 빈도는 이 실험에서만 쓴다.
  - 조건마다 3회. 두 설정을 번갈아 실행하고(회차마다 먼저 하는 쪽을 바꾼다) 같은 세션에서 `on`도 다시 잰다.
- **차이를 인정하는 기준:** 실험 1과 같다. 지표(p50, p99, 서버 CPU, 처리량)별로 `off`의 **중앙값이 `on` 3회의 최솟값~최댓값 범위 밖**이면 차이가 있다고 본다. 범위 안이면 "차이를 확인하지 못했다"고 쓴다. 합격 판정은 기존 합격 기준을 그대로 쓴다.
- **결정 규칙:** `off`가 지연(p99)을 낮추는 방향으로 위 기준을 넘고 처리량·오류·CPU가 나빠지지 않을 때만 기본값 변경을 검토한다. 그 외에는(차이 없음, 또는 `off`가 더 나쁨) 단순한 기준 설정(`on`)을 유지한다.
- **환경 기록:** 같은 PC에서 다른 프로그램(게임, 메신저)이 실행 중이다(끌 수 없음). 각 실행 직전에 전체 CPU 사용률을 2초 샘플로 기록해 배경 부하가 실행마다 크게 달랐는지 확인한다. 이 값이 높은 실행이 있으면 결과 기록에 표시한다.
- **한계(미리 적어 둠):** 루프백에서는 실제 네트워크와 달리 ACK가 매우 빨라서 Nagle의 영향이 작게 나올 수 있다. 이 실험의 결론은 이 환경(Windows 루프백)에 한정한다.

## 측정 도구에서 겪은 문제

| 문제 | 원인 | 수정 |
| --- | --- | --- |
| 연결 50개, 생성기 CPU 3%인데 "생성기 포화"로 판정됨 (스케줄 지연 p99 15ms) | 윈도우의 기본 타이머 해상도가 약 15.6ms라서 타이머가 정해진 시각보다 최대 15.6ms 늦게 깨어남. 생성기가 바쁜 것이 아니었다 | 부하 생성기가 실행되는 동안 `timeBeginPeriod(1)`로 해상도를 1ms로 올림 (스케줄 지연 p99 15.19ms에서 1.51ms로) |
| 기준 측정에서 Idle 500(3회)과 Idle 10,000(1회)이 생성기 CPU 0.4~6%인데도 "포화"로 판정됨 (스케줄 지연 p99 약 15ms) | 같은 타이머 해상도 문제가 일부 실행에서 다시 나타남. 윈도우 11이 해상도 요청을 무시한 것으로 의심되지만 원인은 증명하지 못했다. 이후 짧게 재현했을 때는 정상이었다 | 해상도 요청을 무시하지 않도록 프로세스를 명시적으로 제외(`PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION`). 원래 결과는 보존하고 두 조건을 재측정(6회 모두 합격) |
| 연결 만 개 단위로 반복하면 다음 실행의 연결이 실패할 수 있음 | FIN으로 닫은 쪽에 TIME_WAIT가 남아 임시 포트(약 16,000개)가 참 | 측정이 끝난 뒤에는 RST로 닫음(`SO_LINGER` 0) |

이 두 가지는 측정 도구의 문제이며 서버 코드의 문제가 아니다. 도구가 잘못된 결론(서버 한계 또는 생성기 포화)을 내지 않는지 시험 실행으로 먼저 확인하는 것이 중요했다.
